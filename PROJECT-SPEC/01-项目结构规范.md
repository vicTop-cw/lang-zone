# PROJECT-SPEC/01 — 项目结构规范

> 本文件规定 FIST 下发的项目级任务的标准目录结构与规模纪律。**AI 生成或修改的项目必须符合本规范。**

---

## 1. 标准目录结构

```
<project_dir>/
├── PROJECT-SPEC/        ← 项目规范（FIST 下发时注入，或引用 FIST 的 PROJECT-SPEC/）
├── src/                 ← 源码（按项目实际技术栈组织）
├── tests/               ← 测试（测试对 + 回归，见 03）
├── docs/                ← 设计文档（架构/规范，只增不删不改）
├── reports/             ← 进度报告（按日期子文件夹，见 04）
├── corpus/              ← Ω-spec JSON 测试对（见 05）
├── README.md            ← 项目说明（必填）
└── CHANGELOG.md         ← 变更记录（必填）
```

**说明**：
- 目录可裁剪（如纯脚本项目无 `src/`），但 `README.md`、`CHANGELOG.md`、`reports/` 为必填；
- 项目级任务执行者**仅能操作 `project_dir` 内文件**（FIST 第 12.4 节原子任务执行者约束）。

## 2. 模块规模铁律

| 规则 | 说明 |
|---|---|
| **阈值** | 单个源文件超过 **3000 行**（不含注释），即视为规模超标 |
| **动作** | 立即建立文件夹，把该文件按职责拆分到子模块（`__init__.py`/`mod.rs` 为入口） |
| **触发即做** | 在超过 3000 行**当时**就拆，不等到"有空再重构" |
| **为什么** | 3000 行是"人脑一次能完整理解的上限"；超过后增量修改容易破坏既有语义 |

> 与 Omega 测试原则（03 §3 否定主义）呼应：文件过大 = 覆盖度难保证 = 红灯难定位；拆小文件是"否定主义"的工程化落地。

## 3. 目录职责

| 目录 | 职责 | 禁止 |
|------|------|------|
| `src/` | 源码实现 | 放测试、放报告 |
| `tests/` | 测试对 + 回归 | 放生产代码 |
| `docs/` | 设计/规范文档 | 事后修改历史文档 |
| `reports/` | 进度报告（按日期子文件夹） | 修改历史报告 |
| `corpus/` | Ω-spec JSON 测试对 | 放非 JSON 文件 |
