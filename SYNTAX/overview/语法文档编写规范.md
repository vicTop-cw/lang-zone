# Lang-Zone 语法文档编写规范

> 规范版本: 1.0 · 最后校订: 2026-08-04
> 本文件是 SYNTAX/ 目录**所有语法文档**的编写准绳（meta-规范）。
> 修改任何语法文档前，必须先遵循本规范。

---

## 〇、总原则：文档只写「当前语法规则」

语法文档是**语言现状的唯一权威描述**。它只回答一个问题：

> **当前 LZ 的合法语法是什么？**

它**不回答**（也**不该出现**）以下问题：

- 这个语法过去是什么样的？
- 谁在什么日期改过它？
- 它为什么改成这样？
- 某个旧写法被什么替代了？
- 实现状态如何（解析器是否已支持）？

**一句话铁律**：语法文档里出现的一切文字，都必须是对「**现在的合法语法**」的正面描述；凡是提及「旧 / 新 / 之前 / 曾经 / 废弃 / 替代 / 兼容 / 已移除 / 改名为 / 历史上 / 不再 / 已改 / 目前仅 / 当前实现」等时间性、变更性、实现性措辞，一律视为**违规**。

---

## 一、禁用话语清单（写文档时逐条自查）

以下措辞**不得**出现在语法文档正文、注释、脚注中：

| 禁用类别 | 示例（违规） | 正确写法 |
|----------|--------------|----------|
| 变更叙述 | 「`break :label` 语法**废弃**，改 `break NAME`」 | 「标签由 `block NAME:` 定义，`break NAME` / `continue NAME` 引用之」 |
| 旧新对比 | 「`::` 已**废弃**，路径用 `.`」 | 「路径分隔符是 `.`；`::` 不是有效路径语法」 |
| 历史遗留 | 「**旧设计**曾让 `def` 自动升级为生成器」 | 「生成器用 `iterator` 或 `func *:` 声明；`def` 只定义普通函数」 |
| 兼容性说明 | 「声明式配置（**向后兼容**）」 | 「声明式配置与定义式等价，二选一」 |
| 语义演变 | 「`guard` **原先只能用在函数体内**，现已放宽」 | 「`guard` 可在任意作用域使用」 |
| 校订痕迹 | 「**历史上曾反置** `*` 与 `&`，2026-08-04 校订已纠正」 | 「`&x` 取引用，`*ptr` 解引用」 |
| 实现状态 | 「**当前实现**仅支持…」「解析器**尚未**支持…」 | 直接写合法语法；未支持的语法**不写进文档**（见 §五） |
| 动机叙述 | 「引入 `block` 后，`:` 职责**收敛**为…」 | 直接写 `:` 的当前职责 |
| 冗余强调 | 「**不再**使用 `pub` 关键字」 | 「字段可见性由前缀 `.` / `._` 表达」 |
| 过渡说明 | 「两表单**互不重叠**」等为解释性内容 | 保留**纯语义解释**，去掉变更意味 |

**自查方法**：写完一段后，删除其中所有「时间 / 变更 / 实现」词（废弃、曾经、改为、如今、已、被替代、兼容、历史上、校订、当前实现、后续、将来），若句子仍完整成立，则该段符合规范。

---

## 二、文档应有的组成部分

每份语法文档按以下结构组织（顺序固定）：

```
1. 标题 + 版本块（规范版本 / 最后校订 / 关联文档）
2. 〇 速览（定位 + 一句话定义）
3. 一、语法定义（EBNF 优先）
4. 二、…（按主题展开；每个语法特性：语法 → 语义 → 示例 → 边界）
5. 错误语法边界（正反示例并重）
6. 与相关文档的交叉引用
```

**每个语法特性**的标准写法（四要素，缺一不可）：

1. **语法**：EBNF 或模板（`块级：code block`）。
2. **语义**：直接陈述该构造做什么（现在时，无「允许 / 支持」以外的演进措辞）。
3. **示例**：至少一个正面示例；有歧义处配负面示例（`❌`）。
4. **边界**：约束、限制、编译期规则（用「必须 / 不可 / 报错」正面表述）。

---

## 三、正面表述规则

1. **写「必须 / 是 / 由…表达」，不写「不能再 / 不再 / 已被」**。
   - ❌ 「`break :label` 已废弃，不能再使用」
   - ✅ 「标签由 `block NAME:` 定义；`break NAME` 引用该标签」
2. **写「X 是 Y」，不写「X 曾为 Z，如今是 Y」**。
3. **版本号只递增，不回溯**：改文档时更新头部 `规范版本`（次版本 +0.1）与 `最后校订`（当天日期），并在改动的章节**直接写新规则**，不保留旧规则痕迹。
4. **引用文档用编号 + 名称**（如 `见 05b §4.3`），不引用「上一版 / 旧文档」。

---

## 四、错误语法边界的写法

「错误语法边界」章节展示的是**当前非法写法**（反面教材），不是历史。

- ❌ 「❌ `macro bad(a: int)` — 该写法已不允许」❌（提及变更）
- ✅ 「❌ `macro bad(a: int) -> Tokens` — 错误：macro 签名固定 `Tokens -> Tokens`」✅（直接给当前约束）

负面示例统一用 `❌` 前缀 + 一句「错误：<当前规则>」；错误示例的注释**只说明当前为什么错**，不叙述演变。

---

## 五、未实现 / 设计中的语法

1. **未实现的语法不写入语法文档正文**。若确需记录（如供评审），必须：
   - 单独放入 `overview/缺失语法特性报告.md`（那里允许讨论实现状态与计划）；
   - 语法文档内**不留**「尚未实现 / 待实现」字样。
2. 已定稿但尚未实现的语法，按「已定义规则」正常书写（文档描述语言现状，实现由编译器对齐文档）。

---

## 六、示例的卫生要求

1. 示例代码必须**能通过文档自身声明的规则**（不自相矛盾）。
2. 示例注释里**不出现**「（这是新的）/（老写法是…）/（以后会…）」。
3. 示例中**不使用**文档未定义的语法（除非该示例本身是错误边界）。
4. 删掉与主题无关的示例（如 `struct Meta = x: int` 这类无关占位，见 §一 自查法）。

---

## 七、与 overview/ 的分工

| 位置 | 内容 | 允许提及历史 / 实现 / 计划？ |
|------|------|:------------------------------:|
| `SYNTAX/*.md`（正文规范） | 当前语法规则 | ❌ 绝对不允许 |
| `SYNTAX/overview/缺失语法特性报告.md` | 未实现 / 计划 / 实现差距 | ✅ 允许 |
| `SYNTAX/overview/项目进度报告.md` | 进度 / 校订记录 | ✅ 允许 |
| 本文（meta-规范） | 怎么写文档 | ✅（本文是规范本身） |

> 若你在正文规范里发现了历史叙述，请把它**改写成纯规则**（本规范 §一），或**迁移到 overview**，而不是删掉规则本身。

## 八、提交前检查清单

- [ ] 全文无「废弃 / 曾经 / 改为 / 已 / 兼容 / 历史 / 校订已纠正 / 当前实现 / 尚未」等时间性、变更性、实现性措辞（§一 清单）
- [ ] 每个特性含「语法 + 语义 + 示例 + 边界」四要素（§二）
- [ ] 负面示例只说明「当前为什么错」（§四）
- [ ] 示例全部符合文档自身规则、无无关占位（§六）
- [ ] 头部 `规范版本` 已递增、`最后校订` 为当天日期（§三）
- [ ] 交叉引用编号有效（§三.4）
- [ ] 未实现内容已移入 overview（§五）
