## 一、语法设计不一致与不合理

### 1.1 冒号换行要求不一致 🔴 Critical

**问题**: `while` 和 `for` 循环要求冒号后必须换行+缩进，但 `guard` 和 `match case` 允许单行写法。

| 语句 | 换行要求 | 单行是否允许 |
|------|:---:|:---:|
| `while cond: body` | 强制换行 | 不允许 |
| `for x in xs: body` | 强制换行 | 不允许 |
| `guard cond else: body` | 规范要求换行 | **允许** (单行不报错) |
| `case pat: body` | 规范要求换行 | **允许** (单行不报错) |

**源码位置**: `parser/stmt.rs` (guard 的 else 分支有单行回退) 和 `parser/expr.rs` (match case 的 `:` 分支有单行回退)

**测试验证**: `_test_colon_newline.lz` 编译通过，`guard x > 0 else: return "fail"` 和 `case 1: print("one")` 均不报错

**建议**: 统一为强制换行+缩进（方案 A），移除单行回退逻辑

### 1.2 文档声称功能与实现状态严重不符

**问题**: `00-权威语法规范.md` 标记了大量 `✅`（已验证），但实际代码生成器中大量功能标记为 `❌`（未验证），且测试套件中 122 个文件仅 59% 通过 rustc 编译。

**典型不一致**:
- 规范中 `guard` 标记 `✅` → 实际 codegen 中 `guard let` 标记 `❌`
- 规范中 `break` 标记 `✅` → 实际 codegen 中 `break` 标记 `❌`
- 规范中 `continue` 标记 `❌` → 但 token 和 AST 已定义，只是 codegen 未实现
- 规范中 `None` 标记 `❌` → 但 AST 有 `Expr::NoneLit`，codegen 已验证 `✅`

### 1.3 `::` 路径分隔符已废弃但未彻底移除

**问题**: `::` 在词法层报废弃警告，但解析层仍兼容处理。这导致：
- 新用户可能错误使用 `::`，仅收到警告而非错误
- 代码库中两套路径语法并存，增加维护负担
- 集成测试 DCL-IM-001 因 `::` 废弃而失败

### 1.4 `let mut` 为 no-op 的语义混乱

**问题**: LZ 默认绑定可变更，`mut` 关键字仅起兼容作用。但 `let` 关键字语义上是"不可变绑定"，这与 `let mut` 为 no-op 矛盾。

**源码位置**: `parser/stmt.rs:486` — "Lang-Zong 默认绑定可变更，`mut` 为 no-op 兼容"

**建议**: 要么移除 `mut` 关键字，要么让 `let` 真正不可变

### 1.5 `let owned` 语义矛盾被静默忽略

**问题**: `let owned` 语义矛盾（owned 表示所有权转移，但 let 是绑定），解析器允许但忽略修饰符。

**源码位置**: `parser/stmt.rs:534`

## 二、AST 定义不完善

### 2.1 Pattern 枚举缺少关键变体

**当前 Pattern 定义** (`src/ast/stmt.rs`):
```rust
pub enum Pattern {
    Int(i64),
    Str(String),
    Bool(bool),
    Ident(String),
    Variant(String, Vec<Pattern>),
    Tuple(Vec<Pattern>),
    Wildcard,
}
```

**缺失**:
- 浮点数 pattern (`FloatLit`) — 解析器将浮点 pattern 转为 `Pattern::Str`，语义错误
- `None` pattern — 被当作 `Pattern::Ident("None")`，而非独立变体
- `Some(p)`/`Ok(p)`/`Err(p)` 的嵌套 pattern 走 `Variant`，但语义不够清晰
- 范围 pattern (`0..10`) — 未定义
- 或 pattern (`pat1 | pat2`) — 解析器用复制 arm 的方式处理，AST 无直接支持

### 2.2 Expr 枚举中 Assign 变体与 Stmt::Assign 重复

**问题**: `Expr::Assign` 和 `Stmt::Assign` 同时存在，语义重叠。`Expr::Assign` 仅用于复合赋值表达式位置，而 `Stmt::Assign` 用于语句位置。这种设计增加了 codegen 的分支复杂度。

### 2.3 Stmt::Guard 的 cond 是 Option<Expr>

**问题**: `guard` 语句的 `cond` 字段是 `Option<Expr>`，当 `let_binding` 存在时 `cond` 为 None。但 Rust 的 `let-else` 语法不支持额外条件，LZ 的 `guard let PAT = EXPR else` 和 `guard COND else` 是两种语义不同的结构，用同一个 AST 节点表示不够清晰。

### 2.4 缺少的 AST 节点

| 缺失节点 | 用途 | 现状 |
|---------|------|------|
| `ExternDef` | 外部函数声明 | 无 AST 支持 |
| `ModDecl` | 显式子模块声明 | 无 AST 支持 |
| `ContractDef` | 契约/不变式 | 仅文档提及 |
| `EmbedStmt` | 嵌入资源 | 仅文档提及 |

## 四、类型系统问题

### 4.1 类型推断不完整

**Type::Var (推断变量) 降级为 Unit**: 当类型推断变量未被 zonk 解析时，退化为 `()`（见 `types/def.rs:196`），这会在泛型上下文中产生 `Vec<()>` 等无意义类型

**类型注解缺失时的默认行为不明确**: 无注解参数默认 `i64`，无注解返回默认 `-> i64`，但 `main` 函数例外。这些规则缺乏统一的类型推断框架

### 4.2 类型映射硬编码

**容器类型硬编码**: `List→Vec`, `Dict→HashMap`, `Set→HashSet` 在 `Type::to_rust_type_string()` 中硬编码。如果用户自定义了 `List` 类型，会造成冲突

### 4.3 缺少的类型检查

| 检查项 | 现状 |
|--------|:--:|
| 模式匹配穷尽性检查 | ❌ |
| 泛型约束验证 | ❌ (where 子句未实现) |
| 类型别名循环引用检测 | ❌ |
| trait 方法签名一致性检查 | ⚠️ (部分实现) |
| 可变性借用检查 | ❌ |

### 4.4 `Float` 和 `F64` 重复

**问题**: `Type::F64` 和 `Type::Float` 是等价的（都映射到 `f64`），但 AST 中同时存在两个变体，增加混淆。

## 六、架构与工程问题

### 6.1 编译器测试覆盖率低

**问题**: `cargo test --lib` 仅 404 个测试，对于编译器项目来说偏少。编译器核心路径（解析、类型检查、代码生成）缺乏单元测试。

### 6.2 错误信息质量差

**问题**: 从集成测试分析可见，LZ 编译失败时错误信息不友好：
- 解析错误仅报告 `Expected X, got Y`，缺少上下文
- 类型错误不提供类型不匹配的具体信息
- 代码生成错误直接暴露 Rust 编译错误，用户看到的是 Rust 错误而非 LZ 错误

### 6.3 集成测试超前于编译器实现

**问题**: 集成测试套件中 60 个测试，仅 25% 通过。主要原因是测试使用了编译器尚未实现的功能：
- `async`/`await` 测试 (ASY-001~006)
- 构建块测试 (BLD-GEN-001/002)
- 魔法方法测试 (DCL-MG-001~006)

### 6.4 文档分散且不一致

**问题**: 语法规范存在于多个位置：
- `hermes/00-权威语法规范.md` — 最新权威规范
- `hermes/00-语法规范-20260726.md` — 备份旧版本
- `hermes/01~05-*.md` — 审计文档
- `_bak/hermes/` — 更旧的备份

多个版本的规范文档并存，容易造成混淆。

### 6.5 自举路径不完整

**问题**: 桥接模块 (`src/bridge/`) 已实现，但自举测试 `_test_bootstrap_integration.lz` 标记为通过，实际自举（用 LZ 编译 LZ 编译器）远未完成。桥接模块依赖 `BridgeRegistry` 运行时映射，而非编译期类型安全。
