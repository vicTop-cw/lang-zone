# LZ 自举前条件完成度分析

> 分析日期: 2026-07-25
> 数据来源: 全量测试回归 (122 个 .lz 文件)、6 轮 Bug 挖掘报告、编译器源码 (80+ 文件, ~30,000 行)
> 编译器版本: `lang-zong.exe` (release build)

---

## 一、自举定义

用 LZ 语言重写 LZ 编译器自身，通过 `LZ → Rust → rustc` 编译链产出自举二进制文件。

当前编译器用 **Rust** 编写：

| 指标 | 数值 |
|------|------|
| 源码文件数 | 80+ |
| 代码行数 | ~30,000 |
| 模块数 | 15 |
| 架构层次 | 5 层 (L1 基础 → L2 语法/宏 → L3 语义/类型 → L4 代码生成 → L5 CLI) |

---

## 二、编译器源码依赖分析

自举要求 LZ 能表达编译器的全部逻辑。以下是编译器使用的 Rust 特性及其 LZ 对应支持状态：

| Rust 特性 | 编译器中的使用 | LZ 对应支持 | 状态 |
|-----------|---------------|------------|------|
| 模块系统 (`mod`/`use`/`pub`) | 15 个模块，80+ 文件 | `import`/`from` | ❌ 完全不可用 |
| 枚举 (带数据) | AST 节点、Token 类型、Result | `enum` with variants | ⚠️ 部分可用 |
| 结构体 (含方法) | 核心数据结构 | `struct` + `def self` | ⚠️ 部分可用 |
| 泛型 (`<T>`) | Vec、HashMap、Option、Result | 泛型函数/结构体 | ⚠️ 部分可用 |
| Trait/Impl | 类型系统核心 | `trait`/`impl` | ⚠️ 部分可用 |
| 模式匹配 (`match`) | 广泛使用 | `match`/`case` | ⚠️ 部分可用 |
| Option/Result | 错误处理 | `Option`/`Result` | ⚠️ 部分可用 |
| 闭包 (`|x|`) | 迭代器、回调 | `|x| expr` | ⚠️ 部分可用 |
| 字符串操作 | 源码处理 | `str` 类型 | ⚠️ 部分可用 |
| 集合 (Vec/HashMap) | 核心数据结构 | `List`/`HashMap` | ⚠️ 部分可用 |
| 文件 I/O | 读取源码、写入输出 | 桥接 `std::fs` | ⚠️ 部分可用 |
| 迭代器链 | 数据处理 | 列表推导/for-in | ✅ 基本可用 |
| 控制流 (if/while/for) | 逻辑控制 | 同义语法 | ✅ 可用 |
| 错误处理 (try/catch) | 异常处理 | `try`/`catch` | ❌ 不可用 |
| 生命周期 | Rust 借用检查 | 无对应 | ❌ 需规避 |
| 智能指针 (Box/Arc/Rc) | 内存管理 | 无对应 | ❌ 需规避 |

## 八、关键结论

1. **当前不具备自举条件**：完成度约 18%，核心障碍是模块系统（完全不可用）和类型系统（50% 可用）。

2. **最大单一障碍**：模块系统（Bug-N20 / Bug-35~39）。编译器有 80+ 源文件，没有模块系统就无法组织代码。

3. **第二大障碍**：`i64`/`usize` 类型不匹配（Bug-N1）。影响 50+ 测试文件，几乎所有集合操作和字符串处理都受影响。

4. **乐观估计**：修复 P0 级 8 个 Bug 后，可以在单文件内编写简单的编译器子集，但完整自举需要修复至少 **25-30 个 Critical Bug**。

5. **建议策略**：先集中修复 P0 阻断级 Bug（模块系统 + i64/usize + 枚举 match），预计可提升完成度到 40-50%，届时可以尝试自举 lexer 等简单模块。
