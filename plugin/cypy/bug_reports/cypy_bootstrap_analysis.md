## 二、自举条件分析：写一个 Cypy 编译器需要什么

### 2.1 编译器四大模块需求

| 模块 | 核心需求 | 所需语言特性 |
|------|---------|-------------|
| **词法器** | 字符遍历、字符串处理、模式匹配 | `for`循环、`match/case`、`str`操作、`list` |
| **解析器** | 递归下降、AST 构造、运算符优先级 | 递归函数、`struct`、`enum`、`match` |
| **类型检查器** | 符号表、类型推断、统一化 | `dict`/`map`、泛型、`Option`/`Result` |
| **代码生成器** | AST 遍历、缩进输出、字符串拼接 | `struct`、`match`、`str`操作、`list` |

### 2.2 逐需求可行性评估

#### 词法器自举需求

| 需求 | 可行性 | 说明 |
|------|--------|------|

| `match ch:` 字符分类 | ✅ | 基础 match 可用 |
| `list[Token]` 列表操作 | ✅ | 已验证 |
| `str` 切片/拼接 | ⚠️ | 字符串方法集待验证 |
| `and`/`or` 布尔表达式 | ⚠️ | 需用 `&&`/`||` 替代 (Bug-R7-1) |
| 字符分类 `ch.isdigit()` 等 | ❓ | 未测试 |

**词法器自举可行性: 60%** — 核心逻辑可用，需规避 `and`/`or` 关键字

### 4.4 结论

**当前自举完成度: ~55%**

**核心结论**:
- Cypy 的**基础语法层**（函数、循环、条件、struct、enum）已足够编写编译器核心逻辑
- **最大障碍是代码生成器**：20 个 AST 节点缺失导致大量语言特性不可用
- **类型系统自身不完善**：类型检查器对 match/guard/泛型/类型别名的支持严重不足
- **Transformers 层形同虚设**：所有转换逻辑被绕过，编译器架构不完整

**自举路线图**:
1. 修复 P0 阻塞项（代码生成器 20 个节点 + class 继承）→ 完成度可达 70%
2. 修复 P1 高优先级项（类型系统 + match/guard）→ 完成度可达 85%
3. 修复 P2 中优先级项（词法器 + 代码生成细节）→ 完成度可达 95%

## 六、编译链分析：.pyd 够用吗？

### 6.1 当前两条编译路径

```
路径 A (Cython):  Cypy(.cypy) → cypyc → .pyx → Cython → C → .pyd
路径 B (Bridge):  Cypy(.cypy) → cypyc → C (Python C API) → .pyd
```

关键发现：**Bridge 路径已经抛掉了 Cython 层**，`bridge_generator.py` + `cypy_bridge/compiler.py` 直接将 Cypy AST 生成为 C 代码。但生成的 C 代码仍然 `#include <Python.h>`，依赖 `PyObject`、`PyModule_Create` 等 Python C API，最终产物是 `.pyd`（Windows 动态链接库，Python 扩展模块）。

### 6.2 三层依赖关系

```
┌─────────────────────────────┐
│  Cypy 源码 (.cypy)           │
├─────────────────────────────┤
│  cypyc 编译器 (Python 实现)  │  ← 当前宿主：Python 写的编译器
├─────────────────────────────┤
│  生成 C 代码 (Python C API)  │  ← Bridge 路径已抛掉 Cython ✅
├─────────────────────────────┤
│  编译为 .pyd                 │  ← 仍是 Python 扩展，需 Python 运行时
├─────────────────────────────┤
│  Python 解释器加载运行       │  ← 还没抛掉 ❌
└─────────────────────────────┘
```

### 6.3 要"抛掉 Python"需要什么

如果要生成**独立可执行文件**（像 Go/Rust 那样不需运行时），Cypy 还需要：

| 需求 | 当前状态 | 工作量 |
|------|---------|--------|
| 自建运行时 (GC/内存管理) | 全靠 Python 的引用计数 GC | 极大 |
| 自建标准库 (IO/字符串/容器) | 全靠 Python 内置类型 | 极大 |
| 直接生成机器码/LLVM IR | 只生成 C 代码 | 大 |
| 链接器/平台适配 | 靠 setuptools | 中 |

### 6.4 自举的务实策略：.pyd 足够

自举目标是"用 Cypy 写 Cypy 编译器"，**不需要编译器是独立可执行文件**。务实路径：

```
阶段 1 (当前):
  Python 写的 cypyc ──编译──→ Cypy 用户代码 ──→ .pyd

阶段 2 (自举):
  Cypy 写的 cypyc ──用阶段1编译──→ cypyc.pyd (新编译器)

阶段 3 (迭代):
  cypyc.pyd ──编译自身──→ cypyc.pyd (自举完成!)
```

**每个阶段产物都是 .pyd**，由 Python 加载执行。Python 解释器在此充当"启动器"角色，这是完全可接受的——就像 Java 编译器是 .jar 需要 JVM、C# 编译器是 .dll 需要 CLR 一样。

### 6.5 结论

| 要抛掉什么 | 状态 | 评价 |
|-----------|------|------|
| 抛掉 Cython | ✅ Bridge 路径已实现 | 直接生成 C，不再依赖 .pyx 中间层 |
| 抛掉 Python | ❌ 暂不需要 | 自举不需要，工作量巨大，可自举后再考虑 |
| 自举用 .pyd | ✅ 完全可行 | Python 作启动器是合理架构 |

**总结：Bridge 路径已经抛掉了 Cython 这层，自举目标产物 .pyd 即可，Python 解释器作为"启动器"是务实的架构选择。**
