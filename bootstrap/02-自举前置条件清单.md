# 自举前置条件清单

## 一、功能完整性门槛

在启动自举之前，以下功能模块必须达到可用状态：

| 模块 | 最低标准 | 验证方式 |
|------|---------|---------|
| 词法分析器 | 正确解析项目全部源码的词法单元，无遗漏无错报 | 全量源码词法回归测试通过 |
| 语法分析器 | 正确构建项目全部源码的 AST，无解析错误 | 全量源码语法回归测试通过 |
| 语义分析器 | 类型检查覆盖所有语言特性，无漏报无误报 | 语义分析测试套件 100% 通过 |
| 代码生成器 | 生成的代码可正确执行，通过全部运行时测试 | 代码生成测试套件 100% 通过 |
| 错误报告 | 错误信息准确、可定位、无崩溃 | 错误注入测试全部通过 |
| 标准库 | 项目自身依赖的标准库 API 全部实现并稳定 | 标准库测试覆盖率达到 95%+ |

> **本项目语境（Lang-Zone）**：词法/语法/代码生成已有黑盒 39/39、语法边界 127/133 的验证，但**尚无端到端（生成 .rs → rustc 编译 → 运行）回归**，
> 且**无 Rust 模块级单测**。语义分析的"类型检查"在转译架构下主要由下游 rustc 承担。
> 启动自举前，建议先将"代码生成器"门槛细化为"端到端 lzc→rustc→run 全绿"，详见 `04-当前项目自举具体方案.md`。

## 二、质量门槛

| 指标 | 门槛值 | 说明 |
|------|--------|------|
| 单元测试覆盖率 | ≥ 85% | 核心模块不低于 90% |
| 集成测试通过率 | 100% | 不允许有任何失败的集成测试 |
| 已知 Bug 数量 | P0/P1 清零 | 所有高优先级 Bug 必须在自举前修复 |
| 性能基准 | 不低于外部工具链的 50% | 自举耗时过长会导致开发流程不可用 |

> **本项目语境**：当前 Rust 模块级单测覆盖率为 ~0%，集成测试仅停留在文本断言层。
> 在允许启动 L1 前，至少应补齐端到端集成测试（将 `run_tests.py` 升级为 lzc→rustc→run 闭环），
> 并将 P0/P1 Bug 清零（已知项：字面量溢出静默归零/inf、悬空 `^` 静默接受、缩进不匹配静默忽略等）。

## 三、基础设施门槛

| 基础设施 | 要求 |
|----------|------|
| CI/CD 流水线 | 已搭建，支持自动化构建与测试 |
| 产物发布机制 | 能够产出可独立分发的二进制/包 |
| 版本管理 | 明确的版本号策略，每次构建有唯一标识 |
| 回归测试套件 | 包含自举验证专用的端到端测试用例 |

> **本项目语境**：CI 与产物发布机制当前未在仓库内体现；`run_tests.py` 为本地测试驱动。
> 自举启动前需搭建专用 CI（与日常开发流水线并行），并将 Rust 工具链版本冻结为基准参照（见 `03-自举执行计划.md` 阶段 0）。
