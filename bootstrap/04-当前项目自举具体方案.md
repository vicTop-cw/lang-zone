# 当前项目自举具体方案

## 一、项目现状评估

### 1.1 项目基本事实

- **项目类型**：转译型（transpile）编译器。将自研语言 **Lang-Zone（`.lz`）** 源码翻译为 **Rust 源码**，
  再交由 `rustc`/`cargo` 编译为原生二进制。本项目**不直接生成机器码**，仅做语法层转译，复用 Rust 的类型系统、所有权与优化器。
- **当前开发语言**：Rust（Edition 2024）。
- **目标语言 / 后端**：Rust（单后端，阶段 0 设计）。
- **编译器实现源码**：`src/*.rs`（Rust，共 4 个模块：`token.rs` 词法 / `parser.rs` 语法 / `codegen.rs` 代码生成 / `main.rs` CLI）。
  **即编译器本身目前不是用 Lang-Zone 编写。**
- **语言生态源码**：全部 `.lz` 文件——分布于 `ready/`、`test-suite/`、`tests_buildblock/`、`tests_boundary/`、`workbuddy/plan/` 等。
  这些才是"项目自身可被自身工具链处理"的源码。

### 1.2 外部依赖工具链列表

| 依赖 | 用途 | 是否可去除 |
|------|------|-----------|
| Rust toolchain（`rustc`/`cargo`，edition 2024） | 构建编译器本体 + 编译 `lzc` 生成的 Rust | 当前**不可去除**（即 target 后端） |
| Rust 标准库（`std`：HashMap/HashSet/Vec/Thread 等） | codegen 生成代码的直接依赖 | 不可去除，除非自建后端 |
| 系统链接器（`cc`/linker） | 原生二进制链接 | 不可去除 |
| Python 3（`run_tests.py` 测试驱动） | **仅测试**，非构建依赖 | 可去除（替换为 Rust/Shell 测试 harness） |

> **关键架构约束**：由于后端即 Rust，本项目在现有架构下**无法脱离 `rustc` 完成"从源码到原生二进制"的全链路自举**。
> 这正是转译型语言自举与"自举生成机器码"语言（如 Rust 自举）的根本区别，须在自举路径中明确处理（见第二节）。

### 1.3 当前测试覆盖率（真实数据，2026-07-22）

| 测试层 | 范围 | 结果 | 说明 |
|--------|------|------|------|
| 黑盒功能/边界/构建块/异常测试 | `test-suite/` 39 例 | **39/39 通过（100%）** | **文本级断言**（断言生成 .rs 含子串），非端到端 |
| 语法边界测试 | `tests_boundary/` 133 例 × 4 维度 | **127/133 通过（95%）** | 6 例失败均为 RUSTC_ERROR / 悬空 `^` 等语言能力边界，非编译器崩溃 |
| Rust 模块级单元测试（`#[test]` / `#[cfg(test)]`） | `src/*.rs` | **缺失（≈0%）** | `Cargo.toml` 无 dev-dependencies，源码无测试模块 |
| 端到端测试（生成 .rs → rustc 编译 → 运行 → 比对） | 全量 `.lz` | **缺失** | `TEST_REPORT_001` 第 5.2 节已建议补充 |

> **覆盖率结论**：编译器**前端正确性**已被较好验证（黑盒 100%、边界 95%），但
> **(a) codegen 产出能否被 rustc 干净编译运行**、以及 **(b) Rust 源码自身的回归保护** 仍是空白。
> 这是启动 L2 前必须补齐的缺口（详见文档 02 质量门槛）。

### 1.4 已知主要差距（按优先级）

1. **【架构级】编译器非自托管**：`src/*.rs` 是 Rust，Lang-Zone 当前只把 `.lz` 翻成 Rust，不编译 Rust。
   因此"用 Lang-Zone 编译 Lang-Zone 编译器"在现有架构下不成立 → 需重新界定自举对象（见第二节），或规划编译器自托管（路线 B，更高阶目标）。
2. **【测试级】缺端到端 + 模块单元测试**：见 1.3。
3. **【正确性】字面量溢出静默归零 / inf**（`TEST_REPORT_001` D1）：`9999...9` → `IntLit(0)`；`1e400` → `FloatLit(inf)`。应编译期 `LexError` 拦截。
4. **【健壮性】悬空 `^` 被静默接受**（c017）：`b = a ^` 未被解析期拒绝，静默生成可编译代码。
5. **【健壮性】缩进不匹配被静默忽略**（c130/c132，`token.rs::handle_indent`）：深层语句错位被收为顶层 `const` 而不报错。
6. **【能力边界】`with`/`spawn`/`yield`/`async` 运行时映射缺失或不完整**：`__exit__` 未定义、`std::thread::spawn` 生成代码类型不匹配、`async main` 被 rustc 拒绝。
7. **【能力边界】`Range`/`Vec`/推导的 Display 与类型推断缺口**（c044/c103/c127/c128）。
8. **【一致性】规范与实现/示例分歧**：`hermes/00` 用 `->` / `case =>`，而 `ready/demo.lz` 仍用 `: int` / `case X:`；
   编译器对 `->` 返回类型的实际支持**未验证**（一致性审查报告 §三 A）。
9. **【命名】目录与包名不一致**：已于 2026-07-29 将 crate 名统一为 `lang-zone`/`lang_zone`（`Cargo.toml` 的 `name` 与 workspace 成员一致），已解决。

## 二、自举路径设计

> **核心决策**：由于后端即 Rust 且编译器由 Rust 编写，本项目的"自举"需**分两条路线**推进，
> 避免被"编译器必须自托管"这一高阶目标阻塞近期进展。

### 路线 A（务实，近期可达 L1–L3）

**自举对象 = 全部 `.lz` 生态源码**（标准库、示例、测试样例）。用 `lzc` 编译它们，生成 .rs，再经 rustc 构建为可运行程序；
目标是让这部分**不再依赖任何手写 Rust 配套**。

#### 第一步：依赖梳理与最小化

- 列出 `.lz` 生态编译所需全部外部依赖：仅 `rustc` + `std` + 链接器（无可去除依赖；Python 仅测试）。
- 识别"可由本项目自身产出替代"的依赖：当前无（因所有产物最终都落回 Rust）。
  因此本步在本项目等价于 **确认最小外部基座 = Rust toolchain**，并将其冻结为基准参照（见文档 03 阶段 0）。
- 制定依赖裁剪计划：消除 `.lz` 样例对"手写 `.rs` 配套"的隐式依赖（如 `test_hello.rs` 是否由某 `.lz` 生成，需对齐）。

#### 第二步：核心模块先行

- 选取最独立、成熟的 `.lz` 模块作切入点：建议 **`test_hello.lz` / `ready/` 中的工具或示例脚本**
  （已验证可完整转译并运行，存在 `test_hello.lz` ↔ `test_hello.rs` ↔ `test_hello.exe` 对照）。
- 建立该模块的自举构建流程：`lzc test_hello.lz → test_hello.rs → rustc → ./test_hello`，
  并与现有 `test_hello.exe` 做 stdout 行为比对。
- 验证行为等价性：输出完全一致。

#### 第三步：逐模块攻克（按依赖从底层到上层）

```
构建块 prelude(=: / ~: / *: 闭包 + __Pack)
    → 基础类型 / 字面量
    → 控制流 / 模式匹配
    → 函数 / 泛型 / struct / enum / trait / impl
    → 标准库 ready/
    → 示例与测试样例集
    → 完整 .lz 生态源码被 lzc 统一编译
```

> **映射说明**：模板中的"标准库基础类型 → 词法分析器 → 语法分析器 → 语义分析器 → 代码生成器 → 完整编译器"序列，
> 在本项目中映射为**生态源码的编译顺序**（因其不编译编译器本身）。若未来走路线 B（自托管），该序列才指编译器源码自身的模块顺序。

#### 第四步：全链路贯通

- 端到端自举：`lzc` 编译全部 `.lz` → rustc 构建 → 得到可运行程序；建立自动化验证流水线（diff 输出 + rustc 干净编译 + 运行断言）。
- 配套补齐端到端测试（弥补 1.3 的测试空白），使每一次 `.lz` 变更都经"lzc → rustc → run"回归。

### 路线 B（理想，长期达 L4）

**编译器自托管**：用 Lang-Zone 重写编译器 `src/*.rs` 的核心（或整体），使 `lzc` 自身可由 `lzc` 编译。这需要：

- Lang-Zone 表达力足以实现词法/语法/codegen（当前语言特性已覆盖 struct/enum/generic/trait/closure/构建块，理论可行但需大量工程）；
- 自建或复用后端（脱离 rustc 需 LLVM/Cranelift 后端，或保留 Rust 后端但编译器源码为 `.lz`——即 `.lz` 编译器 → Rust → 编译自身）。
- 路线 B 达成后，方可严格满足 L4（用自举产物再次自举，连续 3 代二进制一致）。

> **建议**：先走路线 A 到 L2/L3，积累端到端验证体系与稳定性；路线 B 作为单独里程碑规划，不在近期前置条件内强制要求。

### 路线 B 试点进展（2026-08-15）

**试点 1 已完成：用 LZ 翻译 LZIR 类型系统**（详见 [`work/lz_ir/README.md`](work/lz_ir/README.md)）：

- ✅ **递归 enum 可用**：LZ 的 `enum IrType: Named(path: str, args: List<IrType>) ...` 自引用类型经 LZ→Rust 生成 `Box<Vec<IrType>>`，编译运行正确——验证了「LZ 能表达编译器核心数据结构」这一路线 B 前提。
- ✅ **display 序列化对齐**：`display_type`/`display_list` 递归渲染，7 个典型类型（`Vec<int>`/`Option<Vec<int>>`/`fn(int, str) -> bool`/`(int, f64)`/`Result<str, int>`/`&mut Vec<int>`/`T`）输出与 Rust 版 `src/ir/display.rs` 逐字符一致。
- 🚩 **暴露 2 个 LZ codegen 真实缺陷**（待修复）：
  1. `List + List` 拼接生成 `Vec + Vec`（E0369）——`binop_str` 对 List 操作数缺特判；
  2. 索引元素按值传参未自动 `.clone()`（E0507）——`f(list[i])` 非 Copy 元素 move。
- 📌 **下一步**：修复上述缺陷 → 扩展翻译 `IrModule`/`Item`/`Stmt`/`Expr` 子集 → 建立 Rust 版 `--emit=ir` vs LZ 版 IR 的 diff 对照回归。

## 三、风险与应对

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| 自举产物有隐藏 Bug（codegen 产生非法 Rust） | 高 | 严重 | 差分测试：`lzc` 生成 .rs 与基准 .rs 逐用例比对；补全端到端"lzc→rustc→run"测试（`TEST_REPORT_001` D5 已证明前端稳健，重点在 codegen↔rustc 边界） |
| 性能严重退化（`lzc` 转译慢） | 中 | 中等 | 设置性能基准线（首次 `lzc` 全量编译 `.lz` 生态耗时），每次自举对比，超标即告警优化词法/语法/codegen |
| 自举迭代不收敛（非确定性构建） | 低 | 严重 | 排查非确定性因素：输出 .rs 中是否含时间戳/随机数/并发顺序；确保 `lzc` 对同输入产出稳定 .rs（可加 golden file 比对） |
| 后端锁定 Rust，无法脱离 rustc | 高（架构性） | 中–高 | 明确将"Rust toolchain"列为自举的**最小可信基座**并在文档中声明；路线 B 规划自建后端以去锁定 |
| 编译器非自托管，L4 严格不成立 | 高（架构性） | 中 | 路线 A 以"生态源码连续 3 代被 `lzc` 稳定编译、产物一致"近似 L4；严格 L4 依赖路线 B |
| 规范与实现分歧导致自举样例误用语法 | 中 | 中等 | 先消歧（一致性审查报告 §三 A/B）：验证并统一 `->` / `:`，`case =>` / `case :`，同步 `demo.lz` |
| 人员投入不足 | 中 | 中等 | 将自举列为项目里程碑，纳入迭代规划 |
