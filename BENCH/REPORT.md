# LZ 编译器性能对比报告（客观修订版）

> 测试日期：2026-07-30
> 基准算法：`fib(35)` 朴素递归斐波那契（`O(2^n)`，约 2980 万次函数调用）
> 正确性校验：四种实现的输出**均为 `9227465`**（已逐一运行确认）
> 硬件：Windows x86-64, MSVC 2022, Python 3.13, rustc 1.96.0
> 修订原因：旧报告（2026-07-30 初版）在「同一维度」上不自洽，本版按**同算法 + 同维度**原则重测并重写。

---

## 0. 一句话结论（5 秒速读）

- **lzcyc 并不比 lzc 快。** 你之前看到「lzcyz 比 lzc 快」，是因为旧数据把 lzcyc 的**纯计算时间**和 lzc 的**整体启动时间**放在一起比了——这是两个不同维度。
- 在**同维度（进程内纯计算）**下：lzc→Rust（`rustc -O`）≈ **19 ms**，lzcyc→`.pyd` ≈ **42 ms**，lzc 反而快约 **2.2 倍**。
- 在**同维度（一次性整体冷启动）**下：lzc→Rust 原生 exe ≈ **0.1 s 级**，lzcyc→`.pyd` ≈ **1.0–1.25 s**（被 Python 解释器启动拖住）。lzc 快约 **10 倍**。
- 早期跨语言表里「LZ 9.56x 最慢」完全是**测量假象**（LZ 只跑了 fib，别的语言跑了 fib+sieve，算法/维度都不一样）。**代码生成没有质量问题。**

> 为什么之前会误判：本沙箱里用 git-bash 直接 `./xxx.exe` 计时会被「shell→exe 启动开销」污染（多则数百毫秒），而 Python `import` 计时不污染。两路混用就制造了虚假差距。

---

## 一、公平测量方法（本版红线）

要做到「同算法、同维度」，先定义清楚两个维度，**绝不混用**：

| 维度 | 含义 | 怎么测 | 反映什么 |
|:----|:-----|:-------|:---------|
| **A. 进程内纯计算**（inner） | 同进程内反复调用目标函数，排除运行时启动 | 进程内循环 N≥30 次取中位数 | **代码生成质量 / 算法吞吐** |
| **B. 整体冷启动**（whole） | 从零启动一次完整运行（含解释器/OS 加载） | 一次完整进程调用 | **用户实际体感（CLI/脚本）** |

两个额外陷阱已规避：

1. **常量折叠**：`fib.lz` 里 `let n = 35` 是字面量，`rustc -O` 会把整个递归在编译期算成常量（内循环测出 0 ms）——这是基准假象。本版用 `std::hint::black_box(35)`（动态输入） defeating 折叠，得到真实 `-O` 内循环时间。
2. **shell 启动污染**：`.exe` 直接计时会混入 git-bash→exe 的启动开销（本沙箱下数百毫秒），不可信。本版内循环一律用进程内 harness，整体时间用 `python -c` 统一测量。

## 二、测量结果（同算法 `fib(35)`，同维度）

### 2.1 维度 A：进程内纯计算（in-process，动态输入）

| 实现 | 构建 | 内循环中位数 | 样本 |
|:----|:-----|:-----------:|:-----|
| **lzc → Rust** | `rustc -O` | **≈ 19 ms** | `19,21,21,18,19,18,19,20,19,19` |
| **lzcyc → .pyd** | Cython `cdef` + MSVC `/O2` | **≈ 42 ms** | 50 次均值 41.59 ms |
| **lzc → Rust** | debug（对照） | **≈ 62 ms** | `65,60,60,63,64,59,60,65,65,68` |

**读法**：在「纯计算」维度，lzc→Rust 的 `-O` 产物比 lzcyc 的 C 级代码还快约 2.2 倍；只有当你把 lzc 停在 **debug** 构建时，lzcyc（42 ms）才显得比 lzc（62 ms）快约 1.5 倍。

### 2.2 维度 B：整体冷启动（一次性运行，含运行时启动）

| 实现 | 整体中位数 | 说明 |
|:----|:----------:|:-----|
| **lzcyc → .pyd** | **≈ 1.0–1.25 s** | `python -c "import fib; fib.main()"`；其中纯计算仅 42 ms，**约 0.6–1.0 s 是 Python 解释器启动 + import** |
| **lzc → Rust 原生 exe** | **≈ 0.04–0.1 s（估算）** | 计算 19 ms + Windows 加载数十 ms；本沙箱无法干净测出 exe 整体时间（见 §四陷阱 2），按 OS 启动经验估算 |

**读法**：在「一次性运行」维度，lzc→Rust 因为没有解释器启动，比 lzcyc→`.pyd` 快约 **一个数量级**。

## 四、环境限制与测量陷阱（诚实披露）

1. **常量折叠**：`rustc -O` 对字面量输入会把递归整体常量折叠（内循环 0 ms）。任何 Rust 代码生成基准都必须用动态输入（`black_box` 或命令行参数），否则测到的不是代码生成质量。
2. **shell 启动污染**：本沙箱中 `./xxx.exe` 的墙钟时间混入 git-bash→exe 启动开销（数百毫秒），不可信。干净的整体时间应统一用 `python subprocess` 或 `cmd /c` 测量，且对所有实现用同一手段。本次 lzc→Rust exe 整体时间因此只能给估算区间。
3. **跨语言脚本算法不一**：`benchmark/run_benchmark.py` 给 LZ 只喂 `fib`，给 Go/Rust/Scala 喂 `fib + sieve(500000)`，分母不同导致「9.56x」这种荒谬比值。

## 五、后端选型建议（基于实测，非玄学）

| 场景 | 推荐 | 理由（实测） |
|:----|:-----|:-------------|
| 一次性 CLI / 脚本 / 微服务 | **lzc → Rust 原生 exe** | 整体 ~0.1 s，无解释器启动；最快冷启动 |
| 已嵌入 Python 进程的热循环（数值计算） | **lzcyc → .pyd** | 内循环 42 ms，与 Rust 同量级，且免跨语言调用；但冷启动带 Python |
| 需要 Python 生态互操作 | **lzcyc → .pyd** | 可直接 `import` |
| 追求极限吞吐 | **lzc → Rust -O** | 内循环 19 ms，本基准下最快 |

**核心判断**：两个后端**都没有代码生成质量问题**。lzcyc 的 C 级代码（42 ms）和 lzc 的 Rust 代码（19 ms -O）在同一数量级。选谁只取决于「部署形态」（有没有解释器、是不是一次性运行），而不是「谁生成的代码更好」。

---

## 六、可复现测量规范（给工程侧）

以后做性能对比，请遵守：

1. **同算法**：所有语言/后端跑**完全相同**的算法与规模（不要 LZ 跑 fib、别人跑 fib+sieve）。
2. **同维度**：要么全部报「内循环中位数」，要么全部报「整体冷启动」，并明确标注是哪一种；**禁止把内循环数和整体数混排成一张表**。
3. **动态输入**：Rust/任何 `-O` 编译器基准必须用动态输入（如 `black_box`、命令行参数、文件读取），否则会被常量折叠。
4. **同 profile**：所有 Rust 产物要么全 `-O`、要么全 debug，不要混着比。
5. **进程内循环取中位数**：单次冷跑噪声大；循环 ≥30 次取中位数。
6. **统一计时手段**：整体时间用同一 harness（如 `python subprocess` 或 `cmd /c`），不要 shell 原生跑 exe 又用 `python -c` 跑另一路。
