## 1. 测试范围与目标

### 1.1 被测对象
Lang-Zong (`lang-zone`) 是用 Rust 编写的源码到源码编译器，将 `.lz` 翻译为 Rust：
`src/token.rs`(词法) → `src/parser.rs`(语法 + 构建块语义校验) → `src/codegen.rs`(代码生成) → `src/main.rs`(CLI)。

### 1.2 测试目标
1. **功能正确性**：核心语言特性被正确词法化 / 解析 / 转译。
2. **边界稳健性**：空、极大/溢出数值、超长标识符、深层嵌套、Unicode 等被稳健处理。
3. **异常健壮性**：非法/边界输入必须**优雅报错（退出码 1）**，**不得 panic（退出码 101）**。
4. **缺陷暴露**：识别词法/语法/代码生成中的潜在缺陷与架构风险。

### 1.3 测试设计
黑盒驱动：每个用例提供一段 `.lz`，调用 SUT 的三种模式之一断言不变量：
- `--tokens`：断言词法产物含预期 Token 子串（如 `IntLit(255)`、`LexError`）。
- `--ast`：断言 AST Debug 输出含预期结构子串（如 `pattern: Int(`）。
- 默认（代码生成）：断言生成的 `.rs` 含预期 Rust 子串（如 `Option<i64>`、`__Pack::Tuple`）。
- 错误模式：断言退出码 `1` 且 stderr 含预期信息，且**非 101**。

## 3. 发现的缺陷与风险评估

> 评级：🔴 Blocker ｜ 🟡 建议修复 ｜ 💭 观察/增强 ｜ ✅ 亮点

### 🟡 D1 — 字面量溢出被静默处理（应编译期拦截）
- **现象**：
  - 整数溢出：`x = 99999999999999999999999` → 词法产出 `IntLit(0)`（`i64::from_str_radix` 失败被 `unwrap_or(0)` 吞掉，见 `token.rs::read_number`）。
  - 浮点溢出：`x = 1e400` → 词法产出 `FloatLit(inf)`（`f64::from_str` 将溢出解析为 `+inf`，不报错）。
- **风险**：用户写出溢出字面量时编译器**零警告**。整数静默变 `0` 会在运行期产生极难排查的逻辑错误；浮点 `inf` 仅在运行期暴露。二者都绕过了"编译期应捕获"的健壮性预期。
- **建议**：在 `read_number` 中检测进制/十进制/浮点解析失败或溢出，返回 `Token::LexError`（由 `parse_module` 统一拒绝），给出明确报错（如"字面量超出 i64/f64 范围"）。

### 💭 D2 — 未知类型名透传，内部泛型不递归映射
- **现象**：`map_type` 仅对已知别名 `List/Dict/Set/Option/Result` 做递归映射。若源码出现未知类型名（如误写 Rust 风格 `Vec<int>`），会原样透传，导致内部 `int` 不被映射为 `i64`，生成非法 Rust `Vec<Vec<int>>`。
- **影响**：当前 Lang-Zong 无 `Vec` 关键字，属用户误用；但若未来引入 `Vec` 或用户拼错类型名，编译器不会报错，而是生成无法编译的 Rust。
- **建议**：① 对未知类型名给出警告/错误；② 对形如 `X<...>` 的构造（无论 X 是否已知）也递归 `map_type` 内部参数。

### 💭 D3 — `if`/`match` 仅依赖语句层特判（架构可维护性）
- **现象**：`match`/`if` 能被正确解析（F08、F13、demo 均验证通过），但 `parse_expr` 主链中并无显式 `if`/`match` 表达式解析分支；其可用性依赖 `parse_stmt` 中 `Token::If`/`Token::Match` 的特判调用 `parse_expr`。
- **风险**：若未来支持 `if`/`match` **作为表达式**（如 `let x = if a { 1 } else { 2 }`），当前表达式解析链不会消费它们而报错。
- **建议**：在 `parse_expr` 中显式增加 `if`/`match` 表达式解析分支，与语句层解耦。

### 💭 D4 — 缩进不匹配被静默忽略
- **现象**：`token.rs::handle_indent` 对"列号介于两层缩进之间"的情况仅留空注释（`// 不匹配的缩进，静默处理`），不报错。
- **风险**：缩进错误可能被悄悄忽略，导致语句被错误嵌套，产生难以理解的解析结果。
- **建议**：对缩进对齐错误给出警告或错误（fail-loud），而非静默吞掉。

### ✅ D5 — 异常处理健壮性优秀（亮点）
- 所有非法/边界输入均**优雅报错（退出码 1）或正常返回，零 panic（退出码 101）**。`LexError`、`Parse error`、构建块语义校验拒绝等路径均能给出明确中文错误信息并干净退出。这是高质量的错误处理表现。

### ✅ D6 — `owned` 契约设计巧妙（亮点）
- `owned` 形参通过注入 `compile_error!` 宏，在 Rust 编译期强制要求调用方以 `^` 显式转移所有权（F14 合规通过、F15 违规被拦截）。这是静态契约约束的有效实践。

### 风险评估小结
- **无 Blocker 级缺陷**：无崩溃、无数据损坏、无安全漏洞、无破坏 API 契约的行为。
- **主要风险点**：D1（字面量溢出静默归零/inf），属应在编译期拦截的健壮性问题，建议优先修复。
- **整体风险等级**：低–中。

## 5. 改进建议

### 5.1 缺陷修复（按优先级）
1. **[P1] D1 字面量溢出检测**：在 `Lexer::read_number` 中对进制/十进制/浮点解析失败或溢出返回 `LexError`，给出明确报错。
2. **[P2] D2 类型名校验**：未知类型名告警/报错；对 `X<...>` 构造递归映射内部。
3. **[P3] D4 缩进不匹配报错**：将静默处理改为 fail-loud 警告或错误。
4. **[P3] D3 表达式层 if/match**：在 `parse_expr` 显式支持 `if`/`match` 表达式，消除对语句层特判的依赖。

### 5.2 测试体系增强
5. **端到端测试**：当前为文本级断言。建议将生成的 `.rs` 经 `rustc --edition 2024` 实际**编译并运行**，验证语义正确性（捕获代码生成产生非法 Rust 的情况）。
6. **Golden File 比对**：对关键用例保存"黄金输出"，支持整文件 diff 而非仅子串，提升回归灵敏度。
7. **CI 集成**：将 `run_tests.py` 接入持续集成，任何源码变更自动回归。
8. **边界补充**：最深缩进/嵌套深度限制、超长源码、制表符/空格混合缩进、注释中含 `=:`/`~:` 等边界。

### 5.3 文档与体验
9. 在语言规范中明确：**构建块语法为 `x = callee ~:` / `x = callee *:` / `x =: 块`**（而非 `x ~:`）；** 列表类型为 `List<T>`（非 `Vec<T>`）**——当前仅由代码行为隐含，易致用户误用（本报告的 B05/B06/G02/G03 用例即因测试初期误用语法而暴露）。
