**生成的 Rust（两侧同形，仅细节差异）**：

```rust
pub fn __lz_main() -> i64 {          // ← 根因产物：这里本不该有 `-> i64`
    println!("{}", "hi")             // ← 尾表达式，类型是 ()
}
pub fn main() {
    std::process::exit(__lz_main() as i32);
}
```

### 3.3 判别矩阵：8 个用例把变量隔离干净（全部实测）

| # | 用例 | 形态 | native | rs-lz | 说明 |
| --- | --- | --- | --- | --- | --- |
| b1 | `b1_brace_print` | 花括号 + `print("hi")` | E0308 | E0308 | **复现** |
| b2 | `b2_indent_print` | 同内容、缩进体 | **OK** | **OK** | 对照：唯一差异是花括号 |
| b3 | `b3_brace_tostring` | 花括号 + `print(n.to_string())` | E0308 | E0308 | 与 b1 同因 |
| b4 | `b4_indent_tostring` | 缩进 + `print(n.to_string())` | **OK** | **OK** | ⇒ **`to_string` 无罪** |
| b5 | `b5_brace_assign_last` | 花括号，末语句 `print(m)` | E0308 | E0308 | 与 b1 同因 |
| b6 | `b6_brace_let_only` | 花括号，体里只有 `let` | E0308 | E0308 | **连 print 都不需要**，unit 尾即可触发 |
| b7 | `b7_brace_ret0` | 花括号，末尾补一行 `0` | **OK** | **OK** | ⇒ 块体确实被当**尾表达式**，有值就过 |
| b8 | `b8_indent_probe_to_string` | `probe_to_string` 原文改缩进 | **OK** | **OK** | ⇒ 那 2 件的失败**只**因花括号 |

**b7 是关键**：它证明花括号块体**是被支持的构造**（能编、能跑），所以 b1/b3/b5/b6 的失败不是「语法不支持」，而是「unit 尾的块体 + typed-main 判据」这一处不自洽 ⇒ 定性为**真缺陷**而非预期负例。

### 3.4 根因链（IR 层，三条证据）

**证据 1 —— IR dump 差异**（同一份自举产物里 `__lz_main` 的 IR 构造）：

```rust
// b1（花括号）：ret = Any
Item::FnDef { name: "main", ret: IrType::Any,
              body: vec![Stmt::ExprStmt { expr: Expr::BlockExpr { stmts: vec![…print…],
                                                                  ty: IrType::Any } }] }
// b2（缩进）：ret = Unit
Item::FnDef { name: "main", ret: IrType::Unit,
              body: vec![Stmt::ExprStmt { expr: <print 调用> }] }
```

**证据 2 —— 判据源码**：`src/ir/codegen/decl_gen.rs:982`

```rust
let is_typed_main = f.name == "main" && !is_async_main && f.ret_ty != IrType::Unit;
```

`Any != Unit` 成立 ⇒ 判成 typed main ⇒ 发 `fn __lz_main() -> i64`（同文件 983 / 1066 / 1515 行三处使用），而花括号体的尾值是 `()`。

**证据 3 —— 返回类型推断源码**：`src/ir/builder/convert_decl.rs:1022`

```rust
} else if let Some(tail) = func.body.last() {
    let mut probe = fn_ctx.clone();
    prescan_body_let_bindings(&func.body, &mut probe);
    let mut ty = infer_stmt_type(tail, &probe);   // ← tail 是 Expr(BlockExpr) 时给 Any
```

花括号体的 `func.body` 只有**一条** `Stmt::Expr(BlockExpr)`，`infer_stmt_type` 对 BlockExpr 回 `Any`（未展开块体取最后语句类型）。

**链条**：`BlockExpr → ret=Any`（convert_decl.rs:1022） → `Any≠Unit ⇒ is_typed_main`（decl_gen.rs:982） → `fn __lz_main() -> i64` 而体尾 `()` → **E0308**。

### 3.5 归属模块与修法建议

| 项 | 内容 |
| --- | --- |
| 主责模块 | `src/ir/builder/convert_decl.rs`（函数返回类型推断，1009–1048 行） |
| 放大点 | `src/ir/codegen/decl_gen.rs:982`（typed-main 判据把 `Any` 当「非 Unit」） |
| 是否 rs-lz 缺陷 | **不是**。rs-lz 消费同一份 IR，只是忠实地把 `Any` 渲染成 `i64`（两侧 E-code 逐件一致即证）。**不要按 rs-lz 单开**。 |

**修法 A（推荐，最小）**：`convert_decl.rs` 在 `tail` 是 `AstExpr::BlockExpr` 时展开取块体最后语句的类型。这个写法**代码库里已有**，见 `src/ir/builder/capture.rs:541-547`（闭包路径的同类修复，注释原文点名了这个坑）：

```rust
// fat-arrow 闭包体（|..| => 块）是 BlockExpr：取最后语句类型，
// 否则 BlockExpr 推断为 Any → 闭包 ret=Any → 调用推断 i64（E0308）
AstExpr::BlockExpr(block) => block.last().map(|s| infer_stmt_type(s, ctx)).unwrap_or(IrType::Unit),
```

⇒ def 体路径缺的就是这一步；对齐后 b1 的 `ret` 变 `Unit`，typed-main 不触发，`fn __lz_main()` 无返回类型，`println!` 合法。

**修法 B（兜底，不推荐单独用）**：`decl_gen.rs:982` 把 `Any` 一并排除出 typed-main 判据。能止血，但会掩盖其它 `Any` 推断缺口。

### 3.6 严重度：P3（低），但值得开单

- **面窄**：121 件语料里**只有这 2 件**用花括号体（全量正则扫描 121 个文件，`def <name>(…) = {` 命中数 = 2），且都是 `div-tools/` 根下的 `probe_*` 探针，**不在 DEMO 门禁 327 件里**。
- **性质重**：属「程序被接受、IR 生成成功、只在 rustc 阶段炸」的**静默误编译**——最容易被误判成「rs-lz 又坏了」，而实际两边一样坏。
- **误导性强**：现象长得像「`to_string` 不支持」（样本名就叫 `probe_to_string`），**但 b4/b8 证明 `to_string` 完全正常**。若只看现象开单，会开出一张假单。

### 4.1 结论

### 4.3 反向发现：3 件 `neg_*` 探针没测到它名字声称的东西

这 3 件**输入确实非法**，定性仍是 `预期负例`（计数不变），但它们声称覆盖的诊断路径其实**没被覆盖**——属覆盖漏洞，不是假红：

| 样本 | 名字声称测 | 实际输入 | 实际报错 | 判定 |
| --- | --- | --- | --- | --- |
| `neg_trait_missing_fn.lz` | trait 方法**缺函数名** | `def go(self) -> int`（trait 内单签名，**该形态本身合法**，见 `DEMO/01_basics/traits.lz:6-7`） | `Expected function name, got Go` | `go` 是**保留字**（`src/lexer/lexer.rs:193` `"go" => Token::Go`）。测到的是「关键字当标识符」，**不是**「缺函数名」 |
| `neg_fn_missing_colon.lz` | 参数**缺冒号** | `def f(x: int)` + 体 | `Expected Eq, got Ident("x")` | 冒号写对了，缺的是 `=`。测到的是「缺 `=`」，**不是**「缺冒号」 |
| `neg_macro_unclosed.lz` | **宏未闭合** | `@!def unclosed macro` | `装饰器名缺失或非法（位置 1:1）` | 真正的宏头是 `#!bin macro`（见 `DEMO/09_macros/macro_demo.lz:1`）。测到的是「坏装饰器」，**不是**「宏未闭合」 |

⇒ 建议后续补 3 条真探针：`def (self) -> int`（缺名）、`def f(x int)`（缺冒号）、`#!bin macro` 后宏体未闭合。现有语料对这 3 条诊断是**盲区**。

- 其余 **21 件 `neg_*`**：文件名与报错一一对名（`neg_dict_missing_colon` → 字典缺逗号提示；`neg_enum_dup_variant` → 重复变体；`neg_ref_assign_immutable` → E0384 …），输入本身非法，两侧同报设计好的诊断 ⇒ `预期负例` 成立。
