# Bug: i64::MIN 字面量无法在源码中表示

**状态**: Open  
**发现日期**: 2026-07-31 14:29  
**严重等级**: 🔴 P1 — i64 边界值无法完整表达  
**发现方式**: 边界值测试  
**测试工程师**: 自动化边界测试

---

## 描述

LZ 编译器的 lexer 无法正确解析 `-9223372036854775808`（i64::MIN）的字面量。

**复现**:
```lz
def main() = print(-9223372036854775808)
```

**实际结果**: `Parse error: 无效的整数（可能溢出）: 9223372036854775808`

**对比验证**:
| 字面量 | 结果 |
|--------|:--:|
| `9223372036854775807` (i64::MAX) | ✅ 通过 |
| `0x7FFFFFFFFFFFFFFF` (i64::MAX hex) | ✅ 通过 |
| `-9223372036854775807` (i64::MIN + 1) | ✅ 通过 |
| `-9223372036854775808` (i64::MIN) | ❌ 拒绝 |

---

## 技术根因

`src/lexer/lexer.rs::read_number` 先解析数字的绝对值 `9223372036854775808`，再调用 `i64::from_str_radix(...)` 验证范围。但 i64::MIN 的绝对值 = i64::MAX + 1 = 9223372036854775808，已超出 i64 正数范围。

`-` 号在 lexer/parser 的处理流程：
1. Lexer: 产生 `Minus` token + `IntLit(9223372036854775808)` token
2. `IntLit` 解析时 `from_str_radix` 返回 `Err` → 触发 LexError
3. 错误发生在一元负运算符与操作数结合之前

这与 Rust 编译器不同——Rust 的 lexer 将 `-9223372036854775808` 作为一个完整的负数字面量 token 处理。

---

## 影响范围

- 用户无法直接写出 i64::MIN 的完整字面量
- 变通：`let min = -9223372036854775807 - 1`
- 对于自动生成的 .lz 代码（如 fuzzer 产出），可能产生"无效"的错误报告

---

## 修复建议

### 方案 A: Parser 层修复（推荐）

在 `src/parser/expr.rs` 的 `parse_unary` 中，遇到 `Minus IntLit(val)` 且 `val == 9223372036854775808u64` 时，折叠为 i64::MIN：
```rust
// 一元负 + IntLit 溢出值 → i64::MIN
if op == UnaryOp::Neg && val == 9223372036854775808_u64 {
    return Ok(Expr::IntLit(i64::MIN));
}
```

### 方案 B: Lexer 层修复

在 `read_number` 中，对十进制解析失败但值刚好为 `i64::MIN.abs()` 的情况，允许通过并在 token 中标记"负上下文"：
```rust
// 允许 9223372036854775808 通过（由 parser 层的一元负处理）
if s == "9223372036854775808" {
    return Token::IntLit(9223372036854775808_i64); // 会 wrap 到 i64::MIN
}
```
⚠️ 方案 B 较激进：`9223372036854775808` 的正数形式也变为合法，可能导致歧义。

### 方案 C: 改进错误消息

如果选择不修复，至少将错误消息从"无效的整数"改为：
```
无效的整数（可能溢出）: 9223372036854775808。
提示：i64 范围是 -9223372036854775808 ~ 9223372036854775807。
使用 -9223372036854775807 - 1 表示 i64::MIN。
```
