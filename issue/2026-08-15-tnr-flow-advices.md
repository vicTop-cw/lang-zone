# 2026-08-15 · Tnr 流程建议（供 lz 参考）

> 来源：Tnr 项目同日全流程复盘（语法冻结 → Ω 验证先行 → 语料规范化 → 提交规则）。
> 定位：**建议文档**（非 lz 正文，不参与 lz 语法/实现真值）；供开发 lz 的 agent 与人类参考。
> 背景：lz 已 19 天 / 247 提交 / v164（自举试点 2），自举试点正暴露 codegen 缺陷（v162）——本建议针对"测试完善期"给出可借鉴的工程实践。

---

## 0. 核心判断

lz 不是"才堪堪做到转译"——**自举试点（LZ 翻译 LZIR 类型系统）是编译器验证强度最高的里程碑**。本建议是锦上添花，不是方向修正：**方向（IR 路线 + 自举试点）继续，工程节奏可借鉴 Tnr 的验证先行做法**。

---

## 1. 建议一：把"自举试点"沉淀为自动化回归门禁

**现状**：自举试点暴露 codegen 缺陷（v162：List 拼接/索引传参 clone/BlockExpr 继承），靠人工发现与修复。

**建议**：做成**每次提交自动跑的自举回归**（对齐 Tnr 的 Ω-gate 理念）：

```
自举回归（每次 commit 前 / CI）：
1. 用当前 lzc 编译 LZ 编译器自身源码（bootstrap/ 试点扩大中）
2. 用产物跑现有 DEMO/BENCH 全量
3. 输出 N/N；新缺陷 → 红灯拦截（不许带着自举回归失败提交）
```

**为什么**：自举 = 编译器用自己编译自己，任何 codegen 语义偏差都会被"自身跑不起来"暴露——这是比"测试对"更强的验证（相当于 Tnr 的三端验证的终极形态）。沉淀成门禁后，v162 那类缺陷会在提交前就被拦住，而不是事后人工发现。

---

## 2. 建议二：引入 progress-reports/ 只增不删不改

**现状**：lz 有 v161-v164 的 docs 提交记录，但散落在 commit message 中。

**建议**：按日期归档进度报告（Tnr 的 README/08 同款模式）：

```
progress-reports/
└── 2026-08-15/
    └── 01-进度报告.md     # 只写：做了什么 / 做成了什么 / 修复了啥 / 改了什么
```

**铁律**：**只增不删不改**——已写内容永不删除/修改，新进展追加文末或新文件；更正以"追加更正"记录。

**为什么**：19 天 247 提交，追溯"当时到底发生了什么"需要过程档案；多 agent 协作时，进度报告是沟通的锚点。

---

## 3. 建议三：单文件超 3000 行 → 建文件夹

**现状**：codegen/typer 类文件在自举扩展后容易膨胀。

**建议**（对齐 Tnr README/04 §1）：

| 规则 | 内容 |
|---|---|
| 阈值 | 单个源文件超 **3000 行**（不含注释）= 规模超标 |
| 动作 | 立即建文件夹，按职责拆分（`mod.rs` 入口 + 子模块） |
| 触发即做 | 超线当时就拆，不拖延 |
| 不豁免 | 生成代码、测试代码同样适用 |

**为什么**：3000 行是人脑一次能完整理解的上限；超线后增量修改容易破坏既有语义，自举试点期尤甚（改错会被自举门禁拦，但返工成本高）。

---

## 4. 建议四：提交同步规则——涉及约 5000 行自动同步

**现状**：lz 按版本提交（v161/v162/...）。

**建议**（对齐 Tnr README/02 §3）：涉及约 **5000 行**变更自动同步（git 提交+push，按逻辑分组多笔提交）；或用户明确要求修改规则时立即执行。

**为什么**：避免大改动积压；5000 行阈值让每次同步的 diff 可控、可审。

---

## 5. 建议五：自举推进方向（中期路线）

**现状**：自举试点 2（Match/EnumDef/TraitDef/DuckDef 翻译），类型系统已能自举。

**建议推进**（按风险递增）：
1. **类型系统 → 词法/语法**：试"LZ 翻译 LZ 的 Lexer/Parser"——把自举度推向编译器前端；
2. **自举度 KPI**：跟踪"lzc 源码中 LZ 行数占比"（当前试点在多少，目标 100%）；
3. **全自举目标**：lzc 用 lzc 编译自身（完整自举）——这将是 lz 自我验证能力的里程碑，也是未来"用 Tnr 反写 LZ"这类跨语言闭环的前置实验。

**为什么**：自举度越高，lz 的自我验证能力越强；这正好与 Tnr 侧"三端验证"（Rust 主实现 vs Python 参考 vs 金标准）形成互补——未来甚至可以把"LZ 实现 Tnr 参考端"作为三端的一端。

## 6. 与 Tnr 的跨项目联动（可选，远期）

| 方向 | 说明 |
|---|---|
| **用 LZ 写 Tnr** | 用 lzc 实现 Tnr 编译器/参考实现：既给 lz 一个真实大型案例（dogfooding），又给 Tnr 提供一个独立验证端（三端之一） |
| **用 Tnr 反写 LZ** | 未来 Tnr 成熟后写 LZ 编译器 → 形成互译闭环（详见 Tnr 侧 `arch-plan/09-Tnr-LZ-互写评估.md`） |

> 语料风险提示（写给 Tnr 侧决策）：Tnr 的 Ω 语料是独立 JSON（corpus/*.spec.json，不受实现语言影响）；DEMO 语料是 Tnr 语法（.tnr）。"用 LZ 写 Tnr"只影响编译器源码语言，**不影响语料**——语料错误风险来自实现与 spec 不一致，不来自实现语言。
