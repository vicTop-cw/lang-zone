## 三、新发现 Bug（本次深度测试）

### 🔴 Bug #D1: i64::MIN 字面量无法表示 — P1（编译器缺陷）

**复现步骤**:
```lz
def main() = print(-9223372036854775808)
```

**预期结果**: 编译成功，生成 `-9223372036854775808_i64`

**实际结果**: `Parse error: 无效的整数（可能溢出）: 9223372036854775808`

**技术根因**: `src/lexer/lexer.rs` 的 `read_number` 先解析数字字面量的绝对值 `9223372036854775808`，再用 `i64::from_str_radix` 验证。i64::MIN 的绝对值 = i64::MAX + 1，超出 i64 范围。`-` 号在解析阶段是独立的 `Minus` token，在 parser 层才组合为一元负运算。

**影响范围**: 用户无法直接在源码中写出 i64::MIN 的完整字面量，必须用 `-9223372036854775807 - 1` 绕过。

**严重等级**: 🔴 P1（i64 类型的基础字面量无法完整表达）

**修复建议**: 特殊处理 `-9223372036854775808`：在 lexer 中允许 i64::MIN 的绝对值作为特例，或在 parser 层对一元负 `IntLit(9223372036854775808)` 做常量折叠。

### 🔴 Bug #D2: `str()` 生成无效 Rust 代码 — P1（代码生成缺陷）

**复现步骤**:
```lz
def main() =
    let s = "num: " + str(42)
    print(s)
```
编译为 `.rs`，然后 `rustc --edition 2021 output.rs`

**预期结果**: 生成的 Rust 代码可以通过 rustc 编译

**实际结果**: rustc 报错:
```
error[E0423]: expected function, found builtin type `str`
  --> output.rs:15:24
   |
15 |     let s2 = "num: " + str(42);
   |                        ^^^ not a function
```

**技术根因**: LZ codegen (`src/codegen/expr.rs`) 将 `str(expr)` 原样输出为 `str(expr)`。Rust 中 `str` 是原始字符串类型而非函数，应生成 `format!("{}", expr)` 或 `.to_string()`。

**影响范围**: 所有使用 `str()` 做类型转换的 .lz 代码生成的 Rust 产物无法编译。

**严重等级**: 🔴 P1（生成不可编译的目标代码）

**修复建议**: codegen 中对 `str(args...)` 调用特判，改为 `format!("{}", args...)` 或 `args.to_string()`。

### 🔴 Bug #D3: 字符串拼接生成无效 Rust 代码 — P1（代码生成缺陷）

**复现步骤**:
```lz
def main() = print("hello" + " world")
```
编译为 `.rs`，然后 `rustc --edition 2021 output.rs`

**预期结果**: 生成的 Rust 代码可通过 rustc 编译

**实际结果**: rustc 报错:
```
error[E0369]: cannot add `&str` to `&str`
   |
14 |     let s1 = "hello" + " world";
   |              ------- ^ -------- &str
   |              |       `+` cannot be used to concatenate two `&str` strings
   = note: string concatenation requires an owned `String` on the left
```

**技术根因**: LZ codegen 将 `+` 运算原样输出。Rust 中 `String + &str` 有效（Add trait），但 `&str + &str` 无效。两个字符串字面量在 Rust 中都是 `&str`。

**影响范围**: 所有使用 `"a" + "b"` 字符串拼接的 .lz 代码生成的 Rust 产物无法编译。

**严重等级**: 🔴 P1（生成不可编译的目标代码）

**修复建议**: codegen 中对 `StrLit + StrLit` / `StrLit + expr` 模式特判，生成 `format!("{}{}", a, b)` 或 `a.to_owned() + &b`。

### 🟡 Bug #D4: `||` 无参数闭包与逻辑或冲突 — P2（语法歧义）

**复现步骤**:
```lz
def main() =
    let f = || 42     // 意图：无参数闭包返回42
    print(f())
```

**预期结果**: 编译成功，定义一个返回 42 的闭包

**实际结果**: `Parse error: Unexpected token in expression: PipePipe`

**技术根因**: `src/lexer/lexer.rs:L656` 将 `||` 仅作为 `PipePipe`（逻辑或）token。parser 遇到 `||` 直接当二元运算符处理，无法识别为无参数闭包。

**影响范围**: 无参数闭包语法不可用。变通：`|_| 42` 带 dummy 参数。

**严重等级**: 🟡 P2（功能可用但有不便）

### 🟡 Bug #D5: `0xFFFFFFFFFFFFFFFF` 被拒绝 — P2（十六进制字面量限制）

**复现步骤**:
```lz
def main() = print(0xFFFFFFFFFFFFFFFF)  # u64::MAX = 16位hex
```

**预期结果**: 编译成功（或给出"超出i64范围"的清晰错误）

**实际结果**: `Parse error: 无效的十六进制数字: 0xFFFFFFFFFFFFFFFF`

**技术根因**: lexer 用 `i64::from_str_radix` 解析所有数字。16 位 hex = u64::MAX > i64::MAX，被误判为"无效"而非"溢出"。

**验证**: `0x7FFFFFFFFFFFFFFF`（15位hex = i64::MAX）正常通过 ✅

**影响范围**: 无法使用超过 15 位 hex 的十六进制字面量，即使值在合法范围内。

**严重等级**: 🟡 P2（错误消息比限制更严重："无效" vs "溢出"）

### 💭 Bug #D6: `#` 注释的错误消息对初学者不友好 — P2（错误消息）

**复现步骤**:
```lz
# this is a comment
def main() = print("hello")
```

**预期结果**: `Parse error: 注释请用 // 而非 #。` 或类似引导性错误

**实际结果**: `Parse error: Expected test name`

**技术根因**: `#` 在 LZ 中预留给属性宏（`#[test]`/`#[derive]`），parser 将其解析为属性前缀，遇不到合法属性名即报"Expected test name"。

**影响范围**: Python 习惯用户迁移到 LZ 时感到困惑。错误消息未指明正确方向。

**严重等级**: 💭 P2（误导性错误消息，但功能正确）
