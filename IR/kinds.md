# IR 种类总览（编译器中间表示的分类）

> 本文回答"IR 都有几种"。每种 IR 都回答了三个问题：**用什么数据结构表示程序？**、**保留多少源语义？**、**为谁服务（优化器还是发射器）？**
> 末尾给出对 LZ 的选型建议。

---

## 一、速查表

| # | 类别 | 形态 | 典型代表 | 适合 LZ？ |
|---|---|---|---|:--:|
| 1 | 树 / AST | 语法树 | LZ 当前 `ast/`、Clang AST | 作为**前端内部**，但**不是**跨后端契约 |
| 2 | DAG | 有向无环图（共享子表达式） | 值编号 CSE | 可选内部优化 |
| 3 | 图 IR | CFG / DFG / PDG | LLVM CFG、Soot | 优化用，发射器不直接用 |
| 4 | 线性 IR | TAC / 栈字节码 / 寄存器字节码 | 三地址码、JVM、WASM、Lua | 偏底层，转译非必需 |
| 5 | SSA | 静态单赋值 + φ 节点 | LLVM IR、Cranelift、MLIR | 优化强，但转译**过度设计** |
| 6 | CPS | 续延传递 | Scheme/MLton 编译器 | 函数式语言，LZ 暂不需要 |
| 7 | ANF | 命名中间值 | OCaml、Haskell Core、Rust MIR 近似 | ✅ LZIR-H 的存在形式 |
| 8 | Sea-of-nodes | 节点 + 依赖边 | HotSpot C2、Graal | JVM 系，不相关 |
| 9 | MIR（中层） | 类型化 CFG + SSA 近似 | **Rust MIR** | 可作为 LIR 参考 |
| 10 | MLIR / 方言多层 | 逐级 lowering | MLIR、TVM Relay | LZ 规模暂不需要多层 |

## 二、逐类详述

### 1. 树 / AST（抽象语法树）
- **形态**：直接反映源码结构的树。可进一步分 *CST*（保留所有语法细节）与 *AST*（语义化）。
- **优点**：从 parser 几乎零成本得到；最适合**语法变换、宏展开、源码格式化**。
- **缺点**：冗余（同一子表达式重复成多个节点）；**没有数据流信息**，难做分析；每个后端若各自持有一份 AST，就是当前 LZ 的重复噩梦。
- **LZ 现状**：`lang-zone/src/ast`、`CY/src/ast` 都是这一类——各自一份，重复。
- **定位**：AST 是**前端的内部表示**，不应作为跨后端契约。

### 2. DAG（有向无环图）
- **形态**：在 AST 基础上把"公共子表达式"合并成共享节点（值编号 / CSE）。
- **优点**：消除重复子树，便于常量折叠、公共子表达式消除。
- **缺点**：仍是树状思维，缺控制流。
- **LZ 定位**：可作为 HIR 内部的优化微 pass，不作主契约。

### 3. 图 IR（CFG / DFG / PDG）
- **形态**：基本块（Basic Block）+ 控制边 = **控制流图 CFG**；再加上数据流边（DFG）、程序依赖边（PDG）。
- **优点**：是**所有强优化（死代码、常量传播、寄存器分配）的地基**。
- **缺点**：远离源码，发射器不直接消费。
- **LZ 定位**：属于 LIR/优化层（见 `IR/README.md` 的 LZIR-L ⚪），发射器不需要。

### 4. 线性 / 顺序 IR
把程序拍平成"指令序列"，有三种子形态：
- **三地址码 TAC**：`t1 = a + b`——每指令最多一个操作符、三个操作数。
- **栈式字节码**：操作数放在操作数栈上（JVM、Python bytecode、**WASM**）。
- **寄存器式字节码**：用虚拟寄存器（**Lua**、Dalvik）。
- **优点**：简单、紧凑、易解释执行或映射。
- **缺点**：丢失了高层语义结构（谁调谁、作用域），且 LZ 是**转译到已有编译器的源语言**，再生成字节码属于绕远路。
- **LZ 定位**：非必需。

### 5. SSA 形式（静态单赋值）
- **形态**：每个变量**只被赋值一次**；在控制流汇合点用 **φ 函数**选择来源。依赖**支配树（dominance）**。
- **代表**：**LLVM IR**、Cranelift、GCC-SSA、MLIR。
- **优点**：数据流分析**极其强大**——几乎一切现代优化都建立在 SSA 上。
- **缺点**：从 AST 构造 SSA 复杂（需计算支配前沿、插入 φ）；而且 LZ 的目标是 Rust / Cython，**它们各自的编译器会重新做 SSA 与优化**。在转译器里做 SSA = 造一遍再拆一遍。
- **LZ 定位**：**不推荐作为主 IR**。仅当我们要在 LZ 层做重优化时才考虑（那是 LIR 的事）。

### 6. CPS（续延传递风格）
- **形态**：每个调用都显式传入"下一步做什么"的续延（continuation）。
- **代表**：经典 Scheme 编译器、MLton、部分 Scala 后端。
- **优点**：控制流（异常、非局部跳转、尾调用）表达优雅。
- **缺点**：心智负担重；对转译到命令式语言（Rust/Cython）反而制造麻烦。
- **LZ 定位**：暂不需要。

### 7. ANF（A 范式 / A-Normal Form）✅
- **形态**：介于树与线性之间——**所有非平凡计算都被命名成临时变量**，但整体仍是嵌套树。
  ```
  let t1 = a + b in
  let t2 = call(t1) in
  t2
  ```
- **代表**：OCaml、Haskell Core、Rust MIR 也近似。
- **优点**：既保留结构（易降到多种目标），又让"求值顺序"显式（易发射）；是**转译器最舒服的 IR 形态**。
- **LZ 定位**：**LZIR-H 采用此形态**——强类型树 + 命名中间值，直接对拍 Rust/Cython 表达式。

### 8. Sea-of-nodes（节点海）
- **形态**：所有运算都是节点，靠**数据/控制依赖边**连接，没有显式指令顺序。
- **代表**：HotSpot C2、Graal。
- **优点**：激进优化（特别是 Java 的动态去虚化）。
- **缺点**：与源语言结构完全解耦，发射器复杂。
- **LZ 定位**：不相关（JVM 系专用）。

### 9. MIR（中层 IR）— 参考样板
- **形态**：**强类型 + CFG（基本块）+ 近似 SSA** 的线性 IR。
- **代表**：**Rust MIR**——Rust 在 AST 之后、LLVM 之前用的就是它，负责借用检查、生成代码。
- **优点**：类型完整、控制流清晰、足够做语言级保证（这正是 Rust 用它做 borrow-check 的原因）。
- **LZ 定位**：是 **LZIR-L** 的最佳参考样板——若将来 LZ 要在发射前做"借用检查雏形 / 死代码"等 pass，照 MIR 做即可。

### 10. MLIR / 方言多层 IR
- **形态**：**多层方言（dialect）+ 逐级 lowering**（高层方言逐步降到底层方言）。
- **代表**：MLIR、TVM Relay。
- **优点**：可表达从"高层计算图"到"底层机器指令"的全光谱。
- **缺点**：框架重、概念多。
- **LZ 定位**：当前规模**不需要**多层；LZIR 的两层（HIR/LIR）已够。若未来要接 ML 加速器后端再评估。

## 三、对 LZ 的选型建议（决策表）

| 你的目标 | 该用的 IR |
|---|---|
| 前端内部、宏展开 | 树 / AST（现有 `ast/`） |
| 跨后端**共享契约**（LZ 的核心需求） | **LZIR-H：强类型树 / ANF** ✅ |
| 源→源转译（Rust/Cython） | 高层 IR，不要 SSA/字节码 |
| 语言级优化 pass（死代码/内联） | LZIR-L：CFG + TAC/SSA（参考 MIR）⚪ |
| 自己实现 VM / 解释器 | 栈式或寄存器字节码 |
| 极致优化（接近 LLVM） | SSA（但 LZ 目标是 Rust/Cython，省掉） |

**一句话总结**：LZ 是**转译器（transpiler）**而非**独立 VM**，所以 IR 应当是**高层、强类型、树/ANF 形态（LZIR-H）**，把 SSA / 字节码 / CPS 等留给目标语言自己的编译器。这正是 `IR/README.md` 第三节定下的两层设计。
