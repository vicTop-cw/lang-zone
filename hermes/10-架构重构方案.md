## 〇、遗留 Bug 与架构关系分析

| Bug | 严重度 | 与架构关系 | 重构后影响 |
|-----|:-----:|-----------|:---------:|
| **Bug-48/49** 泛型 impl | 🔴 P0 | **强相关** — typer 的 `build_fn_sig` 对泛型方法签名不完整，方法调用时 `method_registry` 查不到泛型实例的签名 | ✅ **重构后消失** — rustc 直接推断泛型实例化，不需要 LZ 自建 fn_sig |
| **Bug-33/34** 桥接 Result | 🔴 P0 | **中等相关** — `resolve_call_full` 的 `ret_result` 标志在模块限定调用中不生效，导致 Result 未 unwrap | ✅ **简化** — `.unwrap()` 由 strict 模式默认禁止，Result 必须显式 `match` 或 `?`，桥接不再需要隐式 unwrap |
| **N14** with 语句 | 🟡 P1 | **无关** — 纯 parser/codegen 特性，类似 Python `with open() as f:` | ➖ 独立实现 |
| **M11** itor/Stuff | 🟡 P1 | **弱相关** — `STRATEGY_PKG` 在 codegen 中已预留，但惰性求值需要 `yield`/`__next__` 的正确代码生成 | ➖ 独立实现 |
| **N18/N19** 转义 | 🟢 P2 | **无关** — 纯 lexer 层字符串 token 化问题，`\n`/`\t`/`\"` 等转义序列处理 | ➖ 独立实现 |

### 分析详情

#### Bug-48/49：泛型 impl

**根因**: `src/typer/mod.rs` 中 `infer_module` 收集方法签名时：
```rust
fn build_fn_sig(f: &Function, ...) -> Option<FnSig> {
    // requires f.return_type.is_some() — 泛型方法经常无注解
    f.return_type.as_ref()?;  // ← 返回 None，签名注册失败
}
```
泛型容器（如 `List<T>`, `Dict<K,V>`）的 `__iter__`, `__len__` 等方法签名无法注册，导致方法调用时 `resolve_type_name` 找不到 → 回退到自由类型变量 → zonk 默认 Int → 类型错误。

**为什么重构后消失**: 不再自建 fn_sig + 约束求解。rustc 看到 `let x: Vec<T>` 和 `x.len()` 时自动推断 `T` 和返回类型。LZ 只需生成无类型注解的代码（`let x = vec![...]`）。

#### Bug-33/34：桥接 Result 未 unwrap

**根因**: `src/codegen/expr.rs` 中模块限定调用（如 `std.fs.read_to_string("file")`）进入 PathAccess 分支 → `resolve_call_full` → `ret_result=true` → 应追加 `.unwrap()`。但某些代码路径（直接 import 别名）绕过了这个检查。

**重构后简化**: strict 模式默认禁止 `.unwrap()` → 用户必须显式处理 Result → `match result: Ok(v) -> v, Err(e) -> panic(e)` → LZ 代码显式处理，不需要编译器隐式加 unwrap。

## 一、当前架构问题分析

### 1.1 路径语法不统一（`::` vs `.` 混乱）

**现状**: 项目 memory 中记录 "Import: 100% Rust style (`::` only)"，但实际代码中：
- 词法层: `PathSep` token 代表 `::`
- AST 层: `Expr::PathAccess { receiver, segment }` — 用 `.` 风格的字段命名字段
- 代码生成: 直接用 `::` 拼接 Rust 路径

**问题**: 用户书写的 `a.b.c` 在 parser 中被转为 `PathAccess(PathAccess(a, b), c)`，但实际的 LZ 要求用 `a::b::c`。这种不一致导致：
- 用户写 `a.b` 期望字段访问，实际被解析为路径
- 枚举变体 `Option::Some(x)` 和 struct 构造器 `Vec2::new()` 需要 `::`
- 但方法调用又是 `x.len()` 用 `.`
- 开发者在 `.` 和 `::` 之间频繁犯错

### 1.2 类型推断系统过度复杂

**现状**: 1655+ 行自建 HM 类型推断：
```
src/hints/  → constraint.rs, solver.rs, subst.rs, tyvar.rs, unify.rs (HM 引擎)
src/typing/ → bounds.rs, errors.rs, magic_bind.rs, relate.rs, traits.rs, variance.rs
src/typer/  → mod.rs (1513 行，推断管道)
```

**问题**:
- 约束求解复杂且易出 bug
- zonk 将未解析变量默认 `Int/i64`，产生错误类型注解
- 跨函数传播依赖 `fn_registry` + `build_fn_sig`，无法处理递归函数
- 与 rustc 的推断能力重复造轮子
- 自举后仍需 rustc 二次编译——推断结果对最终编译无实质贡献

### 1.3 move 语义导致的用户体验退化

**现状**: 参数默认按值传递（move），对非 Copy 类型造成 `use of moved value` 错误。

**根因**: codegen 中 `gen_param` 未对堆类型自动添加 `&` 前缀。

## 二、路径/枚举语法统一：`::` → `.`

### 2.1 方案

```
LZ 语法中所有路径访问和枚举变体统一使用 `.`：

  import std.bridge.rust.serde_json    （原: std::bridge::rust::serde_json）
  Option.Some(42)                       （原: Option::Some(42)）
  Result.Err("fail")                    （原: Result::Err("fail")）
  my_module.my_function()               （原: my_module::my_function()）
```

### 2.2 改造点

| 层次 | 文件 | 改动 |
|------|------|------|
| Token | `src/lexer/token.rs` | `PathSep` → `Dot` 或复用 `.` |
| Lexer | `src/lexer/lexer.rs` | `::` 不再识别为 PathSep，改为连续错误或直接报告 |
| Parser | `src/parser/expr.rs` | `PathAccess` 改为按 `.` 解析；Type 路径中 `.` 替代 `::` |
| Parser | `src/parser/parser.rs` | import 语句中 `::` 替换为 `.` |
| Codegen | `src/codegen/mod.rs` | `resolve_type_name` 中 Rust 内部仍用 `::`（LZ→Rust 映射） |
| Codegen | `src/codegen/expr.rs` | 路径拼接从 `::` 改为 `.` |
| Bridge | `src/bridge/` | TOML 中 `rust_prefix` 保持 `::`（Rust 侧），LZ 侧用 `.` |
| 测试 | `test-suite/*/*.lz` | 所有 import 和枚举引用改成 `.` |

### 2.3 向后兼容

- `::` 解析为**词法错误**，提示 "使用 `.` 替代 `::`"
- 旧代码自动失败并给出明确迁移指令

## 三、类型推断方案调整：委托 rustc

### 3.1 新架构

```
                  ┌─────────────────┐
  .lz source ──→  │ Parser (no type)│──→ AST (untyped)
                  └─────────────────┘
                           │
                           ▼
                  ┌─────────────────┐
                  │ CodeGen (raw)   │──→ .rs (with _ annotations)
                  └─────────────────┘
                           │
                           ▼
                  ┌─────────────────┐
                  │   rustc         │──→ errors / success
                  └─────────────────┘
                           │
                           ▼ (on error)
                  ┌─────────────────┐
                  │ Error Wrapper   │──→ LZ-friendly diagnostics
                  │ (SourceMap)     │     mapped to .lz line numbers
                  └─────────────────┘
```

### 3.2 改动清单

#### 3.2.1 Codegen 层：类型注解策略

```rust
// 旧: 使用 typer 推断的类型
pub fn foo(x: i64) -> i64 { ... }
let mut y: Vec<String> = vec![...];

// 新: 全部使用 _ 占位符或省略类型注解
pub fn foo(x: _) -> _ { ... }
let mut y = vec![...];  // rustc 推断
```

策略：
1. **参数类型**: 有注解 → 用注解；无注解 → `_`
2. **返回类型**: 有注解 → 用注解；无注解 → 省略（让 rustc 推断）
3. **let 绑定**: 有注解 → 用注解；无注解 → 省略
4. **闭包**: 全部省略类型注解

#### 3.2.2 Error Wrapper 设计

```rust
// src/rustc_error.rs (新文件)
pub struct LzDiagnostic {
    pub severity: Severity,   // Error | Warning
    pub code: String,         // "E0382"
    pub message: String,      // LZ-friendly message
    pub lz_line: usize,       // mapped by SourceMap
    pub lz_col: usize,
    pub suggestion: Option<String>,
}

pub fn wrap_rustc_errors(
    rustc_stderr: &str,
    source_map: &SourceMap,
    lz_source: &str,
) -> Vec<LzDiagnostic> { ... }
```

#### 3.2.3 保留的类型系统

| 模块 | 处理 | 原因 |
|------|------|------|
| `src/hints/` (7 files) | **删除** | HM 推断引擎不再需要 |
| `src/typer/mod.rs` | **删除** | 推断管道不再需要 |
| `src/typing/bounds.rs` | **保留** | trait bound 检查对代码生成仍有用 |
| `src/typing/traits.rs` | **保留** | trait 满足性检查 |
| `src/typing/relate.rs` | **保留** | 子类型关系 |
| `src/types/` | **保留** | AST 类型定义 |

### 3.3 阶段化迁移

| 阶段 | 内容 | 风险 |
|------|------|:--:|
| Phase A | Codegen 改用 `_` 占位符 + 关闭 typer 调用 | 低 |
| Phase B | 实现 `--check` 的 error wrapping（已在 sourcemap 中实现） | 低 |
| Phase C | 删除 hints/typer 模块 | 低 |
| Phase D | 优化 error wrapper（分类、建议、修复引导） | 中 |

## 四、重构步骤与风险控制

### 4.1 执行顺序

```
Step 1: 路径语法统一 (:: → .)           ← 立即执行
Step 2: Codegen 类型占位符化             ← 立即执行
Step 3: Error Wrapper 增强               ← 随后
Step 4: 删除 HM 推断引擎                 ← 稳定后
Step 5: 清理遗留代码 + 回归测试           ← 收尾
```

### 4.2 影响范围评估

| 改动 | 影响文件数 | 风险等级 |
|------|:---------:|:-------:|
| `::` → `.` (parser+lexer) | ~8 | 🟡 中 |
| `::` → `.` (codegen) | ~6 | 🟢 低 |
| `::` → `.` (test files) | ~50 | 🟢 低 |
| typer 关闭 | ~2 | 🟢 低 |
| error wrapper | ~2 | 🟢 低 |
| hints/typer 删除 | ~20 | 🟡 中 |

### 4.3 风险控制

1. **渐进式**: 每步独立提交，可随时回退
2. **测试驱动**: 每步前后运行 `cargo test --lib` + 全量 `.lz` rustc 验证
3. **开关机制**: typer 关闭用 `#[cfg(feature = "legacy-typer")]` 或编译开关，保留旧代码直到新方案稳定
4. **向后兼容**: 旧 `.lz` 文件在 Step 1 后需要批量迁移 `::` → `.`，提供 `lz-migrate` 工具

## 五、迁移工具设计（`lz-migrate`）

```bash
# 自动将 :: 替换为 .（智能跳过代码生成中的 Rust ::）
lzc migrate old.lz > new.lz

# 批量迁移
lzc migrate --dir test-suite/
```

规则：
- `.lz` 源文件中的 `::` → `.`
- 字符串字面量中的 `::` 保持不变
- 注释中的保持原样
