## 二、新增设计层问题（共 8 项）

### 🔴 A. ~~变量可变性设计反转~~ → **已确认: 源码实现为默认可变, 正确**

**源码验证:** `src/lexer/token.rs` 包含 `Let` token, `src/parser/` 解析 `let x = expr` 为不可变绑定。当前实现与 SYNTAX v3.1 一致。

**结论:** 默认可变 + `let` 不可变 是正确的、已实现的设计。`mut` 在变量绑定中为 no-op（仅装饰性），在 `mut self` 参数中有实际语义（`&mut Self`）。**建议保持不动。**

---

### 🟡 B. `@math` 装饰器——默认类型未决

**现象：**
- `01-类型系统.md`：`@math` 无注解参数 → 默认 `int` + Number trait 标记
- `03-函数基础.md`：`@math` 无注解参数 → 默认 `Number`

`int` 是具体类型，`Number` 是 trait——两者语义完全不同。如果 `@math` 让参数变成 `Number` trait 对象，那 `x * x` 的 `*` 需要通过 trait 分发（即生成 `Number::mul(x, x)`），这是 trait 对象调用，有运行时开销，与"零开销转译 Rust"矛盾。

**建议：** `@math` 只是一个标注器——让**无注解参数**的默认类型从 `int` 变成某种"数值泛型"。实际语义应等价于：
```lz
def sq<T: Number>(x: T, y: T) -> T = x * x + y * y
// @math 等价于为每个无注解参数自动插入独立的泛型参数
```
而不是生成 trait 对象。文档需明确这一语义。

### 🟡 C. 函数签名 `def draw(self)` vs `def draw(self: Self)` 不一致

**现象：**
- `06c-trait和impl.md`：trait 方法写 `def draw(self) -> ()`（无 self 类型注解）
- `06a-struct.md`：struct 方法写 `def area(self: Rectangle) -> f64`
- `01-类型系统.md` §1.3：trait 示例写 `def clone(self: Self) -> Self`

三种写法并存，没有明确规则说明何时需要 `: Self`、何时省略。

**建议：** 统一规则：
- **trait 中**：`self` 类型自动推导为 `Self`，可省略注解
- **struct impl 中**：`self` 类型自动推导为当前 struct，可省略注解
- 省略时编译器自动补全，用户也能显式写出

文档在所有示例中统一使用一种风格（建议省略，更简洁）。

---

### 🟡 D. `...` 三重语义——易混淆

**现象：** `...` 在三个上下文中有不同含义：

| 上下文 | 语法 | 语义 |
|--------|------|------|
| trait 抽象方法 | `def draw(self) = ...` | 无默认实现 |
| 可变参数分隔 | `def f(a: int, ..)` | 关键字参数边界 |
| 解构 rest | `let (first, ..) = xs` | 忽略其余 |

用户看到 `= ...` 在 trait 方法中首次出现时，极大概率理解为"待实现"（类似 Python `pass`），而不是"无默认实现必须覆盖"。

**建议：** trait 抽象方法改用 `= abstract` 或单独关键字：
```lz
trait Drawable =
    abstract def draw(self) -> ()
    def bounds(self) -> (f64, f64, f64, f64) = ...  // 也可以继续用...但混用不优雅
```
或至少文档在 trait 章节显眼位置强调 `...` 的特定含义。

### 🟡 E. Prelude 设计——全局函数的归属混乱

**现象：** `99-内置预导入库.md` 列出的全局函数如 `str(x)`, `len(x)`, `clone(x)` 等，实际上调用的底层魔法方法属于 Rust trait（`Display`, `ExactSizeIterator`, `Clone`），这些 trait 不属于 LZ 语言本身。用户看到 `str(x)` 自然认为 LZ 有个叫 `str` 的函数，但实际上 `str` 可能是类型名也是函数名——两者同名。

**问题：**
- `str` 既是类型名（`let s: str`）也是全局函数名（`str(42)`）
- `len`, `bool`, `int`, `float` 同理——类型名与函数名冲突
- 这与 Python 一致，但 LZ 的用户包括 Rust 开发者，他们会困惑"为什么类型可以调用"

**建议：** 这是 Python 的设计，保持即可。但需在文档中明确标注"这些是内置函数而非类型构造器"，特别是与 Rust 开发者的认知差异。

### 🟡 F. 泛型语法 `where T: Clone` vs `where T <: Clone` 残留

**现象：** 
- `03b-函数泛型.md`：使用 `T: Ordered`（冒号语法）
- `00-词法基础.md` §1.7：`T: Trait1 + Trait2`
- 我参与设计的 v1 规范：使用 `where T <: Ord`（`<:` 语法）

当前统一为 `T: Trait` 冒号语法——这是对的，和 Rust 对齐。但需确认存量文档中是否有 `<:` 残留。

---

### 🟡 G. `ref` 和 `mut ref` 与 `&` / `&mut` 的关系模糊

**现象：**
- `ref r = &x` — 变量绑定用 `ref` 关键字
- 函数参数用 `ref x: str` — 参数用 `ref` 修饰符
- 取引用用 `&x` — 表达式用 `&` 操作符

用户需要记住"声明用 `ref`，取值用 `&`"——这是两套符号。Rust 统一用 `&`。

**建议：** 考虑长期统一：
```lz
// 声明引用
r: &int = &x          // 类型用 &T，初始化用 &x
// 代替
ref r: int = x          // 当前
```
但这是大规模 breaking change。至少文档应有一页说明"为何有两种写法"。

---

### 🟡 H. `_` 参数占位符 `f(1, _, 3)` — 编译器自动命名

**现象：** `f(1, _, 3)` 中 `_` 被编译器自动命名为 `__1`，传给函数。

**问题：** 这个功能极其罕见——没有任何主流语言支持。它的价值场景是什么？如果函数 `f` 的第二个参数有默认值，应该用关键字参数而非 `_`。如果没有默认值，传入一个自动命名的值是做什么？

**建议：** 要么砍掉（降低编译器复杂度），要么用明确的文档说明使用场景。目前四个字的说明完全不够。
