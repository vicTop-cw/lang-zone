## 二、未修复 Bug 按根因分类

### 📦 A 类：代码生成逻辑错误（9 个）—— **任何第三方库都解决不了**

| Bug    | 现象                          | 根因                                        | 正确修法                             |
| ------ | --------------------------- | ----------------------------------------- | -------------------------------- |
| Bug-5  | `None` 推断为 `()`             | codegen 把 `None` 标注成 `()` 而非 `Option<_>`  | 检测 `None` 字面量生成 `Option<_>` 占位类型 |
| Bug-6  | `?.` 用 `Iterator::map`      | codegen 对 `?.` 生成了 `.map(...)` 却套在 `()` 上 | 应为 `Option::map`（无外层迭代器）         |
| Bug-7  | 泛型方法丢 `T`                   | `impl<T> Box<T>` 的 `T` 未传到方法签名            | codegen 收集 impl 泛型参数并注入方法        |
| Bug-19 | `\|\|` 链 String 被 move      | `str` 映射 `String` 按值传，链中被多次消费             | 参数生成 `&str` 或调用前 `.clone()`      |
| Bug-20 | `i64` 索引 `String`           | `int`→`i64`，但 Rust 索引需 `usize`            | 索引/切片处生成 `as usize`              |
| Bug-21 | `List.append`→`Vec::append` | 方法映射表把 `append` 错配成 `Vec::append`         | 应映射 `Vec::push`（单元素）             |
| Bug-22 | 重新赋值生成 `let` 遮蔽             | `elif` 内 `x = v` 被当成新声明                   | codegen 区分"首次声明 vs 重新赋值"         |
| Bug-23 | `String != &str`            | `!=` 两侧类型不一致                              | 比较前 `.to_string()` 或转 `&str`     |
| Bug-24 | `print` 字符串拼接错              | 与 Bug-8 同源的 print codegen 分支              | 统一到 `println!("{:?}", ...)`      |

> **关键判断**：这类 bug 的共性是"生成的 Rust 代码片段模式不对"。它们属于**字符串模板 / AST 模式匹配**层面的逻辑缺陷。没有任何 crate 能替你"生成正确的 Rust"——这是编译器自己的责任。

## 三、Rust 生态库调研结果

### 1. `polytype`（用户提到的方向）

- **是什么**：Hindley-Milner 多态类型系统库，通过 unification 做类型推断。提供 `Type`/`TypeSchema`/`Context`，支持 `unify` / `instantiate`。
- 最新 `7.0.1`，MIT，纯 Rust。
- **能做什么**：实现一套"类型 schema 量化 + 实例化 + 统一"的推断引擎。
- **对 LZ 的适用性评估**：
  - ✅ 理论上可增强 B 类（Bug-14/15/18）的推断能力
  - ⚠️ **但 LZ 已有自建 typer（`src/typer/mod.rs`）且已用 unification 跑通大部分场景**。引入 polytype 等于**替换整个类型推断层**，要重写 `Expr`/`Stmt` 到 `polytype::Type` 的映射、所有 `infer_expr` 逻辑、与 codegen 的衔接——工作量和回归风险极大。
  - ❌ **对 A/C/D 类（共 16/19 个 bug）完全无效**。
- **结论**：除非决定"用 polytype 重建类型系统"，否则只为修 3 个 bug 引入它不划算。

### 2. 解析器库（chumsky / lalrpop / pest）

- **chumsky**：parser combinator，主打**错误恢复**和友好诊断，适合编程语言。
- **lalrpop**：LR(1) 生成器，权威处理优先级/结合性。
- **适用性**：可改善 D 类（Bug-16/17）的语法覆盖范围与错误恢复；但同样需要**重写整个 parser**（lz 当前是手写递归下降），且 Bug-16/17 本质只是"少写两个模式分支"，手写修补成本远低于换库。
- **结论**：不推荐为修 2 个解析 bug 换 parser 框架。

### 3. 诊断渲染库（codespan-reporting / ariadne）

- 改善 Bug-14/17 的**错误信息质量**（位置准确、颜色友好），但不修根因。
- 属"锦上添花"，可后续单独引入提升开发者体验。

### 4. 没有"一键修复 codegen"的库

- 调研确认：**不存在**能"给定 LZ AST 自动生成正确 Rust"的通用 crate。代码生成是编译器自有逻辑，必须自修。

## 四、综合建议（不修复，仅建议）

| 方向                          | 建议                                                                                                |
| --------------------------- | ------------------------------------------------------------------------------------------------- |
| **A 类 (9 个 codegen bug)**   | **直接修 codegen 逻辑**，优先级最高。每个都是局部模式匹配/拼接修正，风险低、收益直接。这是根因所在。                                         |
| **C 类 (5 个 trait/impl 校验)** | 新增一个**语义校验 pass**（在 codegen 前检查 trait/impl 一致性），纯新增逻辑，不影响现有链路。                                    |
| **B 类 (3 个推断 bug)**         | 先在当前 typer 内修（Bug-18 是重复 unify 的简易修复；Bug-14/15 是 method-call / 元组上下文 unify 逻辑）。**暂不引入 polytype**。 |
| **D 类 (2 个解析 bug)**         | 在手写 parser 补两个模式分支即可。无需换 chumsky。                                                                 |
| **诊断体验**                    | 后续可引入 `codespan-reporting` 改善报错，非阻塞。                                                              |

### 关于 polytype 的最终判断

> 用户的"引入 polytype 解决类型推断"思路对 B 类**在理论上有价值**，但：
>
> 1. 未修复 bug 中仅 **3/19** 属于类型推断层，其余 16 个与推断引擎无关；
> 2. 引入 polytype 需**替换现有 typer**，成本/风险远高于在现有 typer 上打 3 个小补丁；
> 3. **真正的"重灾区"是 codegen（9 个），没有任何库能代劳**。
>
> **因此建议：先修 codegen 与校验层（覆盖 14/19 个 bug），类型推断在现有 typer 上增量增强，暂不引入 polytype。**
